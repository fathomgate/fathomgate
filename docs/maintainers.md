# Maintainer handbook

The day-to-day rules for changing Fathomgate's Go code, build and release setup. If you're contributing for the first time, you don't need any of this: start with [CONTRIBUTING.md](../CONTRIBUTING.md). A maintainer or reviewer will point you here if a change needs it.

## Checks every Go change must pass

- `gofmt`, `go vet` and `golangci-lint run` must pass; `make lint` runs them.
- The Go that CI and releases build with is the `toolchain` line in `go.mod`; the `go` line stays the floor (ADR 0013). With the default `GOTOOLCHAIN=auto`, a local Go older than the pin downloads it on first use; a newer local Go keeps building with itself. `make toolchain-check` reports whether the Go in use is the pinned one.
- `make vulncheck` (govulncheck, pinned in the `Makefile`) must report no vulnerability reachable from our code; CI runs it on every push, every pull request and weekly. It sets `GOTOOLCHAIN` to the `go.mod` toolchain, so it scans the standard library that ships, regardless of the Go you have installed. A fix is usually a toolchain bump (below) or a module bump, and a module bump follows ADR 0011.
- **Bumping the Go toolchain.** Dependabot does not update the `toolchain` line (dependabot/dependabot-core#13520), so a bump is manual, usually because the weekly govulncheck run failed on a new standard-library advisory or a new Go patch is out. Below, `go1.X.N` is the new release; the version is written only in `go.mod`, so no workflow, Makefile or doc line needs editing:
  1. Find the newest patch of the minor you are on: `curl -s 'https://go.dev/dl/?mode=json&include=all' | grep -o '"go1\.X\.[0-9]*"' | head -1` (`include=all` also lists releases that are out of support, which the default list omits).
  2. `go mod edit -toolchain=go1.X.N`; `go mod tidy -diff` must print nothing.
  3. `GOTOOLCHAIN=go1.X.N make toolchain-check`, `make vulncheck`, then the green gate. After `GOTOOLCHAIN=go1.X.N make build`, `go version -m bin/fathomgate` shows the new toolchain.
  4. Add a `### Security` entry under `[Unreleased]` in `CHANGELOG.md` naming the new toolchain and the advisory IDs it fixes (or "no advisory" for a routine patch).
  5. Open a `build(ci): bump Go toolchain to go1.X.N` pull request with the advisory IDs it fixes; go-reviewer and security-reviewer review it. Moving the toolchain to a new Go minor also needs `GOVULNCHECK_VERSION`, the golangci-lint version and the `Dockerfile` builder checked; raising the `go` floor needs a new ADR. golangci-lint refuses to run when it was built with an older Go minor than the toolchain, so pick a release whose `golangci-lint version` says `built with go1.X` or newer. The `Dockerfile` builder image (`golang:1.X-alpine`) must match the new minor, because it builds with its own Go. Dependabot does not propose a new `golang` minor for the builder: `.github/dependabot.yml` ignores `golang` semver-minor updates, so the builder minor changes only in this bump. The builder is pinned as `golang:1.X-alpine@sha256:<digest>`, so change the tag and the digest together (see base image pins, below).
- **Base image pins.** `Dockerfile` (builder and runtime) and `Dockerfile.goreleaser` (the base of every release image) pin each `FROM` as `tag@sha256:<digest>`, where the digest is the multi-arch image index, never a single-platform manifest (a platform digest would break the arm64 image). Dependabot's `docker` entry proposes digest updates for the same tag monthly; review them like any dependency bump. To re-pin by hand, run `docker buildx imagetools inspect <image>:<tag>` (or `crane digest <image>:<tag>`), check that `MediaType` is `application/vnd.oci.image.index.v1+json` and that it lists `linux/amd64` and `linux/arm64`, and use the top-level `Digest`. Keep the distroless digest identical in both files, and do not change a pin to a debug tag: `snapshot.yaml` fails an image that has a shell or does not run as `nonroot`.
- **golangci-lint.** `make lint` (and the CI `golangci-lint` job, which runs it) downloads the upstream release archive for `GOLANGCI_LINT_VERSION` into `bin/tools/`, checks it against the sha256 pinned in the `Makefile` before unpacking it, then runs `config verify` and `run ./...` under the `go.mod` toolchain once for each of `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`, `windows/amd64` and `windows/arm64` (the release targets, so a build-tagged file that breaks only one of them fails here rather than at tag time), because syscall field types differ per target and a `nolint` needed on one can be unused on another (`LINT_TARGETS` sets the list; `LINT_GOOS`/`LINT_GOARCH` lint a single target). Why this and not the alternatives (T0.20): golangci-lint-action v9.3.0 downloads the archive and extracts it without checking a hash or signature; `go run …@vX` would be verified by the checksum database but builds with whatever Go is local and is a build upstream does not support. A committed hash pins the exact bytes that upstream ships, and it is the same check locally and in CI. Supported hosts are linux and darwin on amd64 and arm64.
- **Bumping golangci-lint.** Dependabot cannot see the version, so a bump is manual: download the new release's `golangci-lint-X.Y.Z-checksums.txt` and the four `linux`/`darwin` `amd64`/`arm64` `.tar.gz` archives, run `gh attestation verify <archive> --repo golangci/golangci-lint` on each (the checksums file itself is not signed or attested), check that `shasum -a 256` matches the checksums file, then update `GOLANGCI_LINT_VERSION` and the four `GOLANGCI_LINT_SHA256_*` lines together. Pick a release built with at least the toolchain's Go minor (bullet above), and note it in `CHANGELOG.md`.
- **Bumping gitleaks.** Also manual (M1-42): download the new release's `gitleaks_X.Y.Z_checksums.txt` and the four `linux`/`darwin` `x64`/`arm64` `.tar.gz` archives, check each archive's `shasum -a 256` against the checksums file and against the `digest` GitHub shows for the asset (`gh api repos/gitleaks/gitleaks/releases/tags/vX.Y.Z --jq '.assets[] | .name + " " + .digest'`; gitleaks publishes no signature or attestation), then update `GITLEAKS_VERSION` and the four `GITLEAKS_SHA256_*` lines together. A new version brings new built-in rules: run `make secrets-control && make secrets-scan` over the full history and judge every new finding in the same pull request, and note the bump in `CHANGELOG.md`. `make secrets-control` must pass on the new version: it catches gitleaks behaviour this setup depends on (a global allow-list skipping whole files in `dir` mode, the patch format of merge diffs, the "commits scanned" log line).
- **The secret scan and its config** (M1-42, security review of PR #198, L1). CI job `gitleaks` scans a pull request's commits twice: with the pull request's own `.gitleaks.toml` and `.gitleaksignore`, and with the base branch's, read with `git show "$BASE_SHA:.gitleaks.toml"` and `git show "$BASE_SHA:.gitleaksignore"`. A pull request that adds an allow-list entry, an ignore fingerprint or a rule change covering its own finding passes the first step and fails the second. There is no label or other override. The one fallback, to the pull request's own files, applies to any base without a `.gitleaks.toml`: the pull request that added the scanner, and any pull request against a branch cut before it. So a change to `.gitleaks.toml` or `.gitleaksignore` lands in its own pull request, reviewed by security-reviewer, before the pull request whose finding it covers; that pull request then merges `main` (no rebase: a fingerprint names a commit) and goes green. Accepted, not covered: the pull request still controls `tools/secrets/scan.py`, `tools/secrets/control.sh`, the `Makefile` and `ci.yaml`, because `pull_request` workflows run the pull request's own files. The project accepts no outside code and push protection is on, so a change to those files is the maintainer's own and gets the maintainer's eye as a security change.
- **Judging a finding.** A real secret is never allow-listed: rotate it and follow `SECURITY.md`. A false positive gets one full fingerprint line in `.gitleaksignore` (`<commit>:<file>:<rule>:<line>`, `make secrets-control` rejects any other form), with the reason above it. Inline `gitleaks:allow` comments are ignored by the scan. The eos-mcp pin in `tests/integration/conftest.py` (the key `eapi.py` contains "api") fires again on every eos-mcp bump: add one fingerprint for the bump's commit each time. Do not add an inline allow, and do not use a commit-free `file:rule:line` entry, which would hide any later finding on that line.
- A change under `.github/workflows/` must pass `make actionlint` (actionlint, pinned in the `Makefile`, config in `.github/actionlint.yaml`). CI runs it on every push and pull request; install `shellcheck` locally to get the same `run:` script checks.
- CI job `windows` (`ci.yaml`) runs `go vet ./...` and `go test -count=1 ./...` on an elevated `windows-latest` runner with `FATHOMGATE_REQUIRE_PRIVILEGED_TESTS=1`, then re-runs the `Windows` tests in `internal/audit` with `-v` and fails unless each one prints `--- PASS` and none prints `--- SKIP`. With that variable set, the symlink, dangling-symlink, junction and other-owner DACL tests fail instead of skipping when they cannot run. On an unelevated Windows host without Developer Mode, leave the variable unset and those tests skip; CI is where they must run. There is no `-race` on Windows; the Linux `go` job covers it.
- CI job `mcp-conformance` (`ci.yaml`) runs `make conformance` on every push to `main` and every pull request, Dependabot's included, with no path filter; it is meant to be a required status check on `main`. It drives the real `fathomgate serve` binary through the official MCP conformance suite (pinned in `tests/conformance/package-lock.json`) for `2025-11-25` and `2026-07-28`, with go-sdk's own conformance everything-server as the upstream. The run fails on a scored check that is not in `tests/conformance/baseline/`, and on a baseline entry that now passes, so a fix deletes its entry in the same pull request. A change to `internal/proxy` or `cmd/fathomgate/serve.go` runs it locally first. Keep the job's `name:` as `mcp-conformance`: branch protection matches it by name.
- **Bumping go-sdk.** A go-sdk bump, including a Dependabot `go-deps` group PR that moves it, must pass `mcp-conformance` before it merges. The bump rebuilds the fixture upstream from the new go-sdk and runs fathomgate built against it, so a behaviour change on either side shows up as an unexpected failure or a stale baseline entry. Re-check the connection wrapper in `internal/proxy` (`tracksConn`): run `grep -n 'mcpConn.(' mcp/*.go` in the new go-sdk module directory (`go list -m -f '{{.Dir}}' github.com/modelcontextprotocol/go-sdk`) and confirm that every type assertion listed in the `tracksConn` comment still fails, or still succeeds, on go-sdk's newline-delimited connection with and without the wrapper, and that there are no new ones. Re-read `mcp/cmd.go` (`CommandTransport.Connect`, `pipeRWC.Close`): the upstream's process tree (ADR 0021, `internal/proxy/tree.go`) relies on go-sdk calling `Command.Start` inside `Connect` and writing nothing before `Connect` returns (on Windows the process is resumed there), and `mirrorShutdown` signals the group `treeSignalLag` after each of go-sdk's shutdown signals, which must still come at `TerminateDuration` and twice that. Reconcile `tests/conformance/baseline/` in the same pull request with a reason on each changed entry, and compare go-sdk's own `.github/workflows/conformance.yml` `CONFORMANCE_VERSION` with the pin in `tests/conformance/package.json` (a suite bump is its own pull request). A go-sdk minor bump is still its own pull request, and the modules it pulls follow ADR 0011.
- A change to `.goreleaser.yaml`, `Dockerfile`, `Dockerfile.goreleaser`, `go.mod`, `go.sum` or the release workflows also runs `snapshot.yaml` (a GoReleaser snapshot with no publishing or signing). Locally: `goreleaser release --snapshot --clean --skip=publish,sign` with GoReleaser v2.18.2.
- **Release notes.** A tag `vX.Y.Z` publishes `docs/releases/vX.Y.Z.md` as its GitHub release page, with the `.goreleaser.yaml` footer appended; `release.yaml` stops before building if the file is missing or empty. Write it in the release pull request, from the `CHANGELOG.md` section that the same pull request cuts from `[Unreleased]` (`.claude/commands/release.md`). Until `fathomgate/homebrew-tap` exists and the image is multi-arch and signed, `.goreleaser.yaml` generates the Homebrew formula without uploading it and builds the image without pushing it.
- Table tests over synthetic requests; no network in `go test`.
- A change to `Evaluate`, the classifier tables, the audit hash or the redaction token format needs a spec update in the same pull request, and usually an ADR.
- Do not add a dependency without saying why in the pull request. `gopkg.in/yaml.v3` is not permitted.

## Licence mechanics

Fathomgate is licensed under the [Functional Source License, Version 1.1, ALv2 Future License](../LICENSE) (`FSL-1.1-ALv2`), except `policies/examples/` and `profiles/`, which are Apache-2.0 with their own `LICENSE` files ([ADR 0034](adr/0034-source-available-under-fsl.md)). `v0.1.0` and every commit before the relicensing remain Apache-2.0 ([NOTICE](../NOTICE)).

- **No outside code for now.** Close a pull request from anyone who is not a maintainer, with thanks and a pointer to open an issue; then write the change yourself if it is wanted. Do not commit text pasted into an issue (a profile, a policy, a regex): write the file yourself from what the issue describes. Accepting outside code needs a contributor licence agreement and an ADR first (ADR 0034 decision 3).
- Sign off your own commits (`git commit -s`); the DCO app still checks every commit in a pull request.
- Every Go, Python and shell source file starts with an SPDX line in its comment syntax (`// ` or `# `), after any `#!` line; Go files have a blank line after it. The id depends on the path: `SPDX-License-Identifier: Apache-2.0` under `policies/examples/` and `profiles/`, `SPDX-License-Identifier: FSL-1.1-ALv2` everywhere else. `python3 tools/licences/spdx.py --fix` adds a missing line and corrects a wrong one; `make licences-check` fails on either. Data files (policies, profiles, fixtures, Markdown) need no header. Do not add per-file copyright lines; `NOTICE` and git history carry authorship.
- A file moved between an Apache-2.0 path and the rest changes licence. Moving FSL code into `policies/examples/` or `profiles/` publishes it under Apache-2.0 at once; do that only on purpose.
- Code copied from another project keeps its own licence notice, and the pull request names the source and its licence. Add it to `EXCEPTIONS` in `tools/licences/spdx.py` with its SPDX id. Its licence must allow distribution inside an `FSL-1.1-ALv2` binary.
- **Release notes state the licence and the conversion date.** `docs/releases/vX.Y.Z.md` has a *Licence* line: `FSL-1.1-ALv2`, converting to Apache-2.0 on the tag date plus two years (for example, a tag of 2026-10-15 converts on 2028-10-15).
- `THIRD_PARTY_LICENSES/` holds the licence text of every module linked into the binary, without versions. A `go.mod` change that adds or drops a linked module, or a bump that changes a module's licence text, runs `make licences` and commits the result; a new module also gets an entry in `NOTICE`. `make licences-check` (CI job `go build / vet / test`, and the GoReleaser before hook) fails otherwise, and fails on a module whose licence it does not recognise or allow. A Dependabot pull request that trips it gets the regenerated folder pushed to its branch before it merges.
- The name is not licensed with the code: see [TRADEMARKS.md](../TRADEMARKS.md).
