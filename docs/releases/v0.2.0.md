Fathomgate v0.2.0 closes M1, "Say no". `fathomgate serve --policy` now decides every tool call before it reaches the upstream server: it works out what the call does, which device it names, and whether your policy allows it. With the shipped `read-only.yaml`, an agent can run `show` commands and read configuration on every device you list, and cannot reload, write or run anything else.

## What M1 denies

Each call is classified from its tool and its payload (`READ_OPERATIONAL`, `READ_CONFIG`, `WRITE_CONFIG`, `EXEC_ARBITRARY`, `INVENTORY_READ`, `LAB_LIFECYCLE`, `LOCAL_ADMIN`), never from what the tool says about itself. The policy's rules run in file order and the first match decides `allow`, `hold` or `deny`. Under `read-only.yaml`:

- **`reload` and anything else outside the read allow-list** are `EXEC_ARBITRARY` and denied by rule `no-exec`, through netdev-ssh-mcp `run_show_command`, upa `send_command_and_get_output` and eos-mcp `run_command` alike. A multi-line command, a control or non-ASCII character, shell metacharacters, a word starting with `-`, or an abbreviation such as `relo` or `conf t` makes a command `EXEC_ARBITRARY` too. A `show` command through a free-form tool is downgraded to `READ_OPERATIONAL` and allowed; `show running-config` and its short forms (`show ru`, `show tec`) are `READ_CONFIG`.
- **A write whose config lines leave configuration mode** (`end` then `reload now`) is `EXEC_ARBITRARY`, not `WRITE_CONFIG`.
- **A device that is not in your inventory** is denied by rule `default:unknown_target` for every class, reads included, before anything is sent. Upstreams such as netdev-ssh-mcp and eos-mcp log in to whatever host the agent names with your device credentials, so this is what keeps them off `core-x.attacker.example`. A hostname pattern never makes a name known; it only adds a role, site or tags to a device you list.
- **An argument the server profile does not name** (eos-mcp `config_path`, netdev-ssh-mcp `username`), a value the upstream would parse as JSON, a call to a device tool that names no device or uses a tag or group selector, and malformed arguments are denied by rule `default:bad_arguments`. A server with no profile has every call that carries arguments denied the same way.

The agent gets the decision as a tool error (`isError: true`), on one line that names the rule and the class, so it can try something safer:

```text
fathomgate denied netdev-ssh-mcp.run_show_command: rule no-exec (class EXEC_ARBITRARY): EXEC_ARBITRARY is denied: the call runs commands outside the read allow-list or outside configuration mode
fathomgate denied eos-mcp.get_version: rule default:unknown_target (class READ_OPERATIONAL): target not in inventory
```

Nothing reaches the upstream for a denied call. The error never quotes the target, the command or upstream text. Every decision is also one `msg=decision` line on Fathomgate's stderr, with the rule, the class, the target names and the session, and never an argument value.

## Upgrading from v0.1.0

**Breaking:** `fathomgate serve` now needs `--policy <file>` or `--no-policy`. With neither it exits 2 before starting the upstream.

- Add `--policy <file> --inventory <file>` and check that `--server` is a server key `fathomgate version` lists (for example `netdev-ssh-mcp`). The server profiles are built into the binary; `--profiles <dir>` replaces them.
- Or add `--no-policy` to keep v0.1.0's pass-through: every call is forwarded unchecked, and Fathomgate warns at every start.

The policy, inventory and profile files must not be writable by other users. Details are in [docs/install.md, *Upgrading from v0.1.0*](https://github.com/fathomgate/fathomgate/blob/v0.2.0/docs/install.md#upgrading-from-v010). The profile format now needs an `args` list on every tool (ADR 0033), and an `inventory.yaml` copied from v0.1.0 that relied on hostname patterns needs its devices listed by name (ADR 0031); CHANGELOG.md has the migration notes.

Test a policy before you use it: `fathomgate policy test` runs `*.test.yaml` files, whose cases can now give a tool call as the agent sends it and check the exact tool error (ADR 0035), and `fathomgate policy eval --profile` shows one decision with its trace.

## What it does not do yet

- **A held call is not run.** Approvals arrive in M3, so a call a `hold` rule matches is not forwarded; the agent gets `fathomgate held <server>.<tool>: rule <id> (class <CLASS>): needs approval, and approvals aren't available yet, so this call was not run.`
- **An `allow` carrying `dry_run`, `diff` or `timed_rollback` is not run in M1** (ADR 0026): the agent gets `fathomgate cannot run …` naming the rule and the obligation. `redact`, `notify`, `require_ticket` and `canary_first` on an `allow` are not enforced yet; the call is forwarded and `serve` warns at start.
- **No redaction.** Device output, secrets included, reaches the agent as the upstream returns it. Redaction at the response serialiser is M2.
- **No audit log.** `--audit` is refused until M4; until then the decision lines on stderr are the record.

## Install

Download the archive for your platform from this release, check it, and put `fathomgate` somewhere permanent:

```sh
# linux or darwin; amd64 or arm64
curl -LO https://github.com/fathomgate/fathomgate/releases/download/v0.2.0/fathomgate_0.2.0_linux_amd64.tar.gz
curl -LO https://github.com/fathomgate/fathomgate/releases/download/v0.2.0/checksums.txt
curl -LO https://github.com/fathomgate/fathomgate/releases/download/v0.2.0/checksums.txt.sigstore.json
# cosign v3; prints "Verified OK"
cosign verify-blob --bundle checksums.txt.sigstore.json --certificate-identity https://github.com/fathomgate/fathomgate/.github/workflows/release.yaml@refs/tags/v0.2.0 --certificate-oidc-issuer https://token.actions.githubusercontent.com --certificate-github-workflow-trigger push checksums.txt
sha256sum -c checksums.txt --ignore-missing      # macOS: shasum -a 256 -c checksums.txt --ignore-missing
tar -xzf fathomgate_0.2.0_linux_amd64.tar.gz
sudo install -m 0755 fathomgate /usr/local/bin/fathomgate
/usr/local/bin/fathomgate version
```

On Windows, download `fathomgate_0.2.0_windows_amd64.zip` (or `windows_arm64`), `checksums.txt` and `checksums.txt.sigstore.json`, run the same `cosign verify-blob` command, compare `Get-FileHash -Algorithm SHA256` with the zip's line in `checksums.txt`, and unzip it.

Then follow [docs/install.md](https://github.com/fathomgate/fathomgate/blob/v0.2.0/docs/install.md): copy `policies/examples/read-only.yaml` and write an `inventory.yaml` listing your devices into a directory only you can write, and connect Claude Code, Claude Desktop or Cursor. Use the full path to `fathomgate`, to the upstream server and to `--policy` and `--inventory` in every client config: desktop apps often start servers without your shell's `PATH`.

Each archive holds the binary, `LICENSE`, `NOTICE`, `THIRD_PARTY_LICENSES/`, `TRADEMARKS.md`, `README.md`, the example policies and their tests (`policies/examples/`), the server profiles (`profiles/`, also built into the binary; ADR 0027) and `inventory.example.yaml`. Binaries are built with `CGO_ENABLED=0` and `-trimpath` by go1.26.8, with go-sdk v1.8.0; `go version -m fathomgate` shows both, and `fathomgate version` lists the built-in profiles with the first 12 hex digits of each file's SHA-256.

Not in this release: a Homebrew formula and a published container image. The `Dockerfile` in the repository builds the distroless image (`nonroot`, no shell) if you want one now; run it with `--init`.

## Verify

- `checksums.txt` lists the sha256 of every archive and SBOM. It is signed with [cosign](https://docs.sigstore.dev/cosign/) keyless signing: `checksums.txt.sigstore.json` is a Sigstore bundle holding the signature, a short-lived certificate issued to this repository's release workflow at this tag, and the public transparency log entry. The `cosign verify-blob` command above (cosign v3) checks all three, then `sha256sum -c` checks each download against the verified list. If `cosign verify-blob` prints anything but `Verified OK`, do not use the download.
- Each archive has an SPDX SBOM next to it: `<archive>.spdx.sbom.json`.

## Security

The gate, the classifier, the closed argument lists, the inventory resolver and the `serve --policy` file checks went through security review before this release, and the release-gate review of 2026-09-26 left no critical or high finding open; the fixes are under Security in [CHANGELOG.md](https://github.com/fathomgate/fathomgate/blob/v0.2.0/CHANGELOG.md). Open items are in the [threat model](https://github.com/fathomgate/fathomgate/blob/v0.2.0/docs/security/threat-model.md). Five need your attention now:

- If you run upa behind a policy that decides any class by device tag or role (such as `lab-open`'s lab writes, or reads of `READ_CONFIG` allowed only on `lab` devices), keep upa's TOML inventory writable only by you (not by the agent, and not by any tool or MCP server the agent can use), and keep its device names one-to-one with the inventory you pass Fathomgate, with each `hostname` being that same device's address. Otherwise an edited TOML can send an allowed lab write to a production device, or return a production device's configuration to a read allowed only on lab devices.
- Fathomgate authorises device names; the upstream resolves them (DNS, `ssh_config`, eos-mcp's `config.ini`). eos-mcp 1.3.0 never checks the device's certificate, whatever `verify` says, and sends its `[DEFAULT]` credentials to a listed host that `config.ini` does not name. List only devices you trust by name, and keep a trusted network and DNS path to them.
- `--no-policy` forwards every call unchecked, as v0.1.0 did. Do not use it in front of devices you care about.
- netdev-ssh-mcp takes a `port` from the agent, so on a console server or jump host a call can reach a different device from the one the policy checked. Do not put console servers or jump hosts in the inventory under device roles.
- upa writes commands, config lines and the start of device output to its stderr, and Fathomgate relays that into its own log. Until redaction arrives in M2, treat that log as holding device configuration.

The release job now runs in a `release` environment and waits for a maintainer's approval before it can mint the signing identity (threat-model row "Release job without a human gate"); the maintainer is currently the only approver, so this is a deliberate pause, not a second person's check. Report a vulnerability as described in [SECURITY.md](https://github.com/fathomgate/fathomgate/blob/v0.2.0/SECURITY.md).
