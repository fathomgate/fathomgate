# Security policy

Fathomgate is a security control. A bug that lets a call reach a device against policy, lets a secret reach an agent, or lets an approval be forged is a vulnerability, not a defect. Report it privately. Do not open a public issue.

## Reporting

- Use GitHub private vulnerability reporting on this repository (Security tab, "Report a vulnerability"). This is the preferred channel.
- If that is unavailable, email SECURITY_CONTACT_EMAIL_PLACEHOLDER with the subject `fathomgate security`.
- Include: version or commit, the upstream server and profile involved, the policy file (with any secrets replaced), the exact `tools/call` arguments, what you expected and what happened. For a redaction gap, include the shape of the line with the secret characters replaced by a made-up value of the same length. Never send a real secret.
- You will get an acknowledgement within 3 days and a first assessment within 10 days. Fixes for confirmed policy, approval or redaction bypasses are released as a patch as soon as they are ready; the advisory is published with the release.
- Credit is given in the advisory and the changelog unless you ask otherwise.

Until the first tagged release, report against `main`.

## Supported versions

| Version | Supported |
| --- | --- |
| `main` | Yes, during pre-release development |
| Latest minor release (`0.x.y` with highest `x`) | Yes |
| Previous minor release | Security fixes only, for 90 days after the next minor |
| Anything older | No |

Dependency advisories for the pinned go-sdk are tracked and re-pinned on every security release of the SDK.

## What counts as a vulnerability

| Class | Example |
| --- | --- |
| Policy bypass | A `WRITE_CONFIG` or `EXEC_ARBITRARY` call reaches an upstream without the decision the policy specifies; a command passes the `EXEC_ARBITRARY` downgrade that should have been blocked; a config read through a free-form tool is not reclassified `READ_CONFIG` |
| Redaction bypass | A secret matching a documented pattern, or of a documented vendor form, reaches the agent in any tool result, elicitation text, error message, diff or audit `args_redacted` |
| Approval bypass | An approval is accepted without server-side identity; `approver_must_differ` can be satisfied by the requester; an EXPIRED or DENIED record can be executed; a retried call executes twice; the webhook accepts an unsigned or replayed request |
| Drift guard bypass | A change different from the approved diff is applied after approval |
| Audit integrity | An event can be inserted, altered or removed without `fathomgate audit verify` failing; a checkpoint verifies against the wrong key; raw output or a secret enters the chain |
| Inventory | An unknown target is treated as known; a stale snapshot is used without `sot: stale`; a live 404 is overridden by a snapshot |
| Upstream trust | A changed tool description is not quarantined; an upstream elicitation is forwarded without origin; upstream sampling is not blocked; header and body mismatch is accepted on HTTP |
| Watchdog | A rollback deadline passes without the rollback being issued or a `rollback_failed` event being written |
| Key handling | The redaction key or checkpoint key is written to the log, blob store, audit event or console |

Not vulnerabilities, but welcome as issues: false-positive redaction, a missing pattern for an undocumented vendor form (use the [redaction gap template](.github/ISSUE_TEMPLATE/redaction_gap.yml)), performance, and upstream servers' own bugs.

## Threat model summary

The full trust boundaries are in [ARCHITECTURE.md](ARCHITECTURE.md#trust-boundaries). In short:

- The agent is untrusted. It may be prompt-injected by device output or by a poisoned tool description. Fathomgate classifies by payload, never by the agent's or the tool's claims, and never takes approver identity from the agent.
- Upstream tool descriptions, annotations and output are untrusted. Descriptions are pinned; annotations only raise a class; output is redacted before the agent sees it.
- Approvers are authenticated server-side: OS user for the CLI, HMAC for the webhook, client principal for MRTR.
- The source of truth is trusted data with unreliable availability; stale data is marked, never hidden.
- The proxy host is trusted. Fathomgate does not defend against an attacker with write access to its keys, database or log directory; frequent checkpoints and an external log sink limit what such an attacker can hide.

Recorded from the T0.2 security review. M0 forwards every call with no policy; these are the known gaps and when they close.

| Schema spoofing: an elicitation schema that hides fields, smuggles instructions in vendor keywords (`x-*`, `$defs`, `allOf`) or nests objects the client renders unpredictably | Closed in T0.3: the schema is rebuilt, never copied (profile-schema 8.4): unknown keywords are dropped, nested objects refused, at most 32 properties, 64 enum values each and 16 KiB rebuilt. | Prompt flood: go-sdk runs an upstream's incoming requests concurrently, so a hostile stateful upstream can fire many `elicitation/create` at once; a stateless upstream can ask up to 16 prompts per round | Closed in T0.3: one prompt open per call and at most 10 prompts per call on every path (a stateful upstream's `elicitation/create`, fathomgate's own prompts to a stateful agent, and `input_required` rounds to a stateless agent, whose count travels in the sealed `requestState`), shared across rounds. | Upstream prompt social engineering: a correctly labelled prompt can still ask the human for a password or an approval | Accepted for M0. The label names the upstream; the human decides. The upstream's own state decides what a repeat means. Base64 malleability does not matter while replays are not deduplicated; it would if they ever are | M3 (approval envelopes carry a single-use pending id) |

Accepted (residual), maintainer, 2026-09-24: a principal that can call a stateful upstream can keep other sessions' prompts on it refused, by ending one call per `OrphanTTL` or by holding a call open (availability only; fails closed; the log names the principal). The only recourse is removing that principal's token; a shorter `OrphanTTL` would give up the confused-deputy protection. From M3 this needs a per-upstream prompt policy or principal binding (threat model, Open). The envelope is bound to its transport and principal since T0.30 (`fg4.` today), not to a session: a stateless request has none, and a stateful agent never receives one. The rule is stated in profile-schema 8.4, *The cross-session attribution rule* | Envelope: closed (T0.30). Prompt availability across principals: M3 (per-upstream prompt policy or principal binding) |
| Content-block `_meta`: `_meta` inside individual result content blocks still reaches the agent | Open | M2 (redaction at the response serialiser) |
| A stateful upstream's `elicitation/create` attributed to the wrong call | Closed in T0.3: relayed only when exactly one call is in flight on that upstream; otherwise refused, and the refusal is only appended to the results of the calls in flight, never put in place of an upstream error or result. Since T0.42 this holds for a prompt the orphan rule refuses too, including when the refusal is worded from the one call in flight (the ADR 0014 case): it is a note on that call, appended to a result the upstream completes, and an upstream error stays the upstream's. Only a prompt attributed to a call (one call in flight, no foreign orphan) can have its refusal stand in for that call's upstream error. Accepted residual: a note tells the agent that an upstream prompt existed on that upstream around the time of its call (existence and timing), never its text, the session or the principal it may have belonged to; and which refusal an agent sees (the orphan reason, or for a stateless agent whether the ADR 0014 wording arrives as a note or as fathomgate's own error) reveals whether another agent session ended a call on that upstream within `OrphanTTL`, the same disclosure the "another agent session's call ... has ended recently" refusal already makes | — |

| MCP05 injection through results: tool result content, including ANSI escapes and prompt-like text, reaches the agent unchanged | Open. Only error messages and stderr are escaped in M0 | M2 (redaction at the response serialiser) |
| Grandchildren survive a kill: the restart, a failed start and shutdown signal only the direct child, so the server behind `npx` or `uvx` can outlive the proxy, holding the upstream's credentials | Closed. Loopback only: `--listen` takes `localhost`, `127.0.0.1` or `[::1]`; any other address, `--listen-remote` and `--listen-host` exit 2. Both loopback families are bound on the port (`127.0.0.1` and `[::1]`), so while Fathomgate runs no other local user can take the one a client resolves `localhost` to; if one is taken, it does not start ([ADR 0023](docs/adr/0023-listener-binds-both-loopback-families.md), T0.52). Fathomgate also holds the port on `0.0.0.0`, `[::]` IPv6-only and `[::]` dual-stack (bound, never listening), so another program cannot bind a wildcard and wait for it to stop; if one already holds a wildcard on the port, Fathomgate refuses to start. Operators should have the supervisor restart Fathomgate at once ([install guide](docs/install.md#remote-agents-over-http)). | Listener connection slots held by a local user without a token: the 128 connections are shared by both loopback addresses, and a connection that sends nothing is closed only 3 seconds after it is accepted | Accepted residual (T0.52): a local user who opens connections faster than they time out (about 43 a second) keeps every slot busy, and agents wait. Availability only; nothing is reached without a token. The listener is loopback-only, and M0 does not defend the proxy's availability against local users ([threat model](docs/security/threat-model.md), resource exhaustion row) | — |

Closed in M0: upstream input requests cross only as origin-labelled form elicitation and only to an agent that declared it; everything else is refused (T0.3, [profile-schema section 8.4](docs/specs/profile-schema.md#84-protocol-eras-_meta-and-input-requests)). Upstream error messages and stderr are labelled with their origin and have control, bidi, zero-width and line-separator characters escaped. The upstream inherits only an allow-listed environment; anything else is passed by name, secrets with `--upstream-env-pass NAME` so their values never reach fathomgate's command line, and `FATHOMGATE_*` never ([ADR 0017](docs/adr/0017-keep-upstream-secrets-off-the-command-line.md)). Passed values of 4 bytes or more are replaced by `[redacted:NAME]` in the upstream's relayed stderr, in upstream error messages relayed to the agent, and in everything fathomgate writes to stderr; no fathomgate error quotes an environment value or an argument that could be one. Tool results are not scrubbed until M2. Reserved `serve` flags are refused wherever they appear. The HTTP listener binds loopback only, on both loopback addresses (T0.52), and needs a token from an owner-only file or the environment on every request (T0.31); tier 2 runs it against a real upstream (T0.33).

The corpus this design answers: Invariant Labs tool poisoning and rug-pulls, Trail of Bits line-jumping and ANSI deception, the MCP specification's security best practices (confused deputy in proxies, token passthrough), OWASP MCP Top 10 (MCP03 tool poisoning, MCP05 command injection, MCP08 missing audit), and arXiv 2603.22489. Links are in [docs/PLAN.md](docs/PLAN.md#sources).

## Hardening guidance for operators

- Run one proxy per credential scope. Upstreams read credentials from their environment; the proxy cannot scope them per call.
- Give upstream secrets (device passwords, `SSH_AUTH_SOCK`) with `--upstream-env-pass NAME` and set them in the client's `env` block or a keychain wrapper, never with `--upstream-env NAME=value`: arguments are visible to other local users (`ps`) and recorded by process auditing (`auditd`, Windows event 4688, Sysmon, EDR). The value then sits in the client's config file, so keep that file out of git or use the client's `${VAR}` expansion ([docs/install.md](docs/install.md#device-credentials)). Values under 4 bytes, and encodings other than those listed in [profile-schema section 8.3](docs/specs/profile-schema.md#83-fathomgate-serve-flags), are not scrubbed, and a value an upstream returns in a tool result reaches the agent unscrubbed in M0.
- With `fathomgate serve --listen`, give each client its own token file and name (repeat `--listen-token-file`), so one can be withdrawn without the others. Token files are read once at startup: a token is withdrawn only by removing its `--listen-token-file` entry (or replacing the file's contents) and restarting Fathomgate. Deleting the file while Fathomgate runs does not withdraw it.
- Give the token to the client as an environment reference, not the value: in Claude Code, `"Authorization": "Bearer ${CLAUDE_FATHOMGATE_TOKEN}"`, with the variable set for the `claude` process alone (`CLAUDE_FATHOMGATE_TOKEN="$(cat <file>)" claude`, or a PowerShell window used only to start it). Never put it in a shell startup file, a PowerShell profile or `setx`: every process Claude Code starts (its Bash tool, hooks, stdio MCP servers) inherits it, and any approved project `.mcp.json` that names the variable sends the token to the `url` it gives. Read a project's `url` and `headers` before approving its MCP servers. Don't name the client variable `FATHOMGATE_LISTEN_TOKEN`. A token pasted into a client's config sits in that file (`~/.claude.json`, or `.mcp.json` with `--scope project`), and `claude mcp get` prints it ([docs/install.md](docs/install.md#remote-agents-over-http)).
- Keep `redact.key_file` and `audit.checkpoint_key` outside the log and blob directories, readable by the proxy user only.
- `fathomgate audit keygen` creates the checkpoint private key owner-only and never overwrites an existing file, symlink or public key. On Unix the key is created with `O_EXCL` and set to mode `0600` regardless of the umask. On Windows it is created with a protected DACL, applied atomically by `CreateFile`, that grants full control to the creating user and `SYSTEM` only and inherits nothing from its folder, so a key under `C:\ProgramData` is not readable by `BUILTIN\Users`. The public key (`<out>.pub`) is written first, is readable by everyone by design, and is deleted again if the private key cannot be written.
- Excluding `BUILTIN\Administrators` from the key's DACL is intentional. Backup software that uses `SeBackupPrivilege` (VSS, `robocopy /B`) still copies the key, and an administrator who needs it recovers it by taking ownership, which is explicit and shows in the file's owner.
- The audit log gets the same owner-only protection when Fathomgate creates it. An existing log is used only if it is a regular file with exactly one link (no symlink, junction or other reparse point, no hard link) and is owned by the user running Fathomgate; anything else is refused with an error naming the reason. Its chain is verified through the open handle first, and only then is it reset to owner-only (mode `0600`, or the owner-only DACL). That reset strips read access you gave a log shipper or any other account: run the shipper as the proxy user, or have it read a copy.
- Elevated on Windows: Fathomgate sets the owner of the files it creates to your user SID, not `BUILTIN\Administrators`, so its own logs still resume when it runs elevated. A log created by another elevated tool is owned by `BUILTIN\Administrators` and is refused (the error names the owner). If you trust that file, give it to the proxy user with `icacls <log> /setowner <user>` and start again.
- What the code cannot do for you: an administrator or root can still take ownership of the key and read it, and a backup or sync tool copies it with the destination's permissions. Keep the key off synced folders (OneDrive, Dropbox) and out of general-purpose backups. To replace a key, delete the old one (and its `.pub`) deliberately; `keygen` refuses to overwrite either. Keys created before T0.12 on Windows keep their inherited ACL: generate a new key, or remove inherited entries with `icacls <file> /inheritance:r /grant:r <user>:F`. On Windows, key and log paths longer than 260 characters currently fail to open (closed, not open).
- Ship checkpoint hashes to syslog or a SIEM so the chain is anchored outside the host.
- Bind the webhook listener to loopback or a private interface, behind TLS termination you control, and rotate the HMAC key with the `key_id` mechanism.
- Start with `policies/examples/read-only.yaml`. Widen from there.
