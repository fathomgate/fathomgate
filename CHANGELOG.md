# Changelog

All notable changes to Fathomgate are recorded here. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html) from `0.1.0`. Until `1.0.0`, a minor version may change the policy or profile file format, with a migration note.

Entries use the project vocabulary: decisions are allow, hold, deny, expired; classes are spelled as in [docs/glossary.md](docs/glossary.md).

- `internal/proxy` Streamable HTTP handler (T0.27, ADR 0016), served by `fathomgate serve --listen` since T0.31 (above): `(*Proxy).HTTPHandler(HTTPOptions)` serves `/mcp` for both eras through a dispatcher on `MCP-Protocol-Version` in front of a stateful and a stateless go-sdk handler that share the one server. Checks in order: a non-loopback `Host` on a loopback bind gets 403, and so does any `Origin` or cross-site `Sec-Fetch-Site`, on every method and before authentication, with no CORS headers. Other paths get 404. A bearer token is required (401 with `WWW-Authenticate: Bearer`); tokens are named principals, kept as SHA-256 digests and compared in constant time, and a principal is attribution only. POSTs in flight are capped at 64 overall and 32 per principal (503 with `Retry-After: 1`), and stateful sessions at 16 overall and 4 per principal. Every 401, 403, 404, 413 and 503 closes the connection. Tool calls in flight are capped at 8 per session and 32 per principal and refused before the upstream. The body limit is 4 MiB. Every write to the agent has a 10-second deadline, so an agent that stops reading costs a bounded time. Deleting a session, fathomgate's own 30-minute idle expiry (no POST in progress) and `Proxy.Close` cancel the session's calls before closing it. A stateful upstream's prompt is relayed only when the one call in flight and every call that ended in the last `OrphanTTL` (5 minutes) on that upstream belong to the same agent session (T0.38, T0.40). `JSONResponse` stays off, and a test pins that no progress follows a result. The exported surface is `HTTPHandler`, `HTTPOptions`, `HTTPPath` and `ErrMCPGODEBUG`; the `http.Server` settings (64 KiB headers, 10 s header timeout, 120 s idle, `Proxy.Close` on shutdown), the 128-connection listener and the `MCPGODEBUG` refusal for exit 2 live, unexported, in `cmd/fathomgate` for T0.31. Session ids are logged only as a hash. Rules in `docs/specs/profile-schema.md` sections 8.4 and 8.5.

- `fathomgate serve --upstream-env-pass NAME` (T0.23, ADR 0017): repeatable; copies `NAME` from fathomgate's own environment (a client's `env` block, a launching shell, a keychain wrapper) into the upstream's, so a device password or `SSH_AUTH_SOCK` never sits on fathomgate's command line, in `ps` or in process-audit records. Every passed value of 4 bytes or more, and its Go-quoted, JSON, percent-encoded, Python byte-escaped and backslash-doubled forms, is replaced by `[redacted:NAME]` in the upstream's relayed stderr on the raw bytes before escaping (split writes and multi-line values included; longest form first; stderr after the final flush is dropped), in upstream JSON-RPC error messages relayed to the agent (before escaping and the 512-byte cap), and in everything fathomgate writes to stderr; shorter values, other encodings and tool results (M2) are not scrubbed. `internal/proxy`: `Command.Secrets []Secret` (added to the child environment at exec time, never in `Command.Env`), opaque `Secret` built with `NewSecret` that formats as its marker in every `fmt` verb, JSON and `slog`, and `NewRedactor`/`Redactor.Redact`, built once. `docs/install.md` "Device credentials" now uses `--upstream-env-pass` with the client `env` block for Claude Code and Cursor, and the tier 2 tests pass the fake device password the same way.

- `internal/proxy` progress relay (T0.17): when the agent's `tools/call` carries a `progressToken` (a string, or an integer of magnitude up to 2^53-1), fathomgate sends the upstream a random token of its own and relays the upstream's `notifications/progress` for that token under the agent's token. Only `progress`, `total` and `message` cross; the message is labelled `[from <server>]`, control characters escaped and capped at 512 bytes plus an ellipsis, and dropped if it reads as an origin label. Notifications for other tokens, after the call, or whose progress does not increase are dropped; at most 10 at once and 5 per second per call, with the newest held-back one sent when a rate slot frees up or, at the latest, before the result. The agent's `_meta` still never crosses. Every relayed upstream string (prompts, progress messages, error messages, stderr lines) now has each backslash doubled, so upstream text cannot spell an escape that reads as fathomgate's, and the origin-label check decodes backslash escapes (`\uXXXX`, `\UXXXXXXXX`, `\xNN`, `\u{H..}`), HTML character references and percent-encoding, failing closed past eight nested layers, and removes HTML tags and markdown punctuation before looking for `[from`. In an elicitation schema, an `enum` value or property name with a backslash is refused and a default that would need escaping is dropped. Conformance `tools-call-with-progress` now passes in both eras. Rules in `docs/specs/profile-schema.md` section 8.4.

- `internal/proxy` (T0.2): an MCP server toward the agent and a go-sdk client toward one stdio upstream. `tools/list` exposes each upstream tool as `<server>.<tool>`; `tools/call` strips the prefix and forwards under the agent's context, so cancellation reaches the upstream. Unknown or unprefixed names get JSON-RPC `-32602` with `reason` `unprefixed`, `unknown_server` or `unknown_tool`. An exited upstream yields a tool error naming it. Upstream JSON-RPC errors are relayed with the label `upstream <server>:`, control characters escaped, a 512-byte cap, and non-standard codes (and `-32602`) mapped to `-32603`. Upstream input requests (elicitation, sampling, roots) are refused by fathomgate (narrowed by T0.3, below). Upstream tool names outside `[A-Za-z0-9_.-]` are not exposed. No policy runs yet. Rules in `docs/specs/profile-schema.md` section 8.
- `internal/proxy` dual-era (T0.3): each side's era is detected on its own (upstream once at connect, `server/discover` then the initialise fallback; agent per request) and logged with `upstream ready`. The agent's `_meta` is never forwarded, and the upstream's result `_meta` is dropped, so a 2025-era agent never sees 2026-era `_meta`. An upstream's form elicitation reaches the agent prefixed `[from <server>]`, its schema rebuilt from an allow-list (at most 32 properties, 64 enum values, 16 KiB; `format` only `email`, `uri`, `date` or `date-time`) with every human-visible string escaped and the form title and every property title labelled; a prompt whose message or schema contains `[from` after case and Cyrillic/Greek/fullwidth/bracket look-alike folding is refused, and refusal texts never quote upstream values: as MRTR `input_required` to a 2026-07-28 agent, whose retry must carry fathomgate's AES-256-GCM sealed `requestState` (the upstream's state and the binding to server, tool, arguments and outstanding ids are encrypted; 30-minute expiry; 96 KiB cap measured after sealing), or as `elicitation/create` to a 2025-era agent; one prompt open per call and at most 10 prompts per call on every path, across rounds. Answers cross only as `accept` with content, `decline` or `cancel`. Sampling, roots and URL-mode elicitation are refused; a stateful upstream's prompt to a stateless agent is refused (ADR 0014). An unattributable prompt's refusal is only appended to results, never put in place of an upstream error. Invalid retries get `-32602` with `reason` `invalid_request_state` or `invalid_input_responses`. Methods of undeclared capabilities (`prompts/*`, `resources/*`, `logging/setLevel`, `completion/complete`) get `-32601`. Server names that read as `fathomgate` (case, `-`, `_` and trailing digits ignored) are reserved (`serve` exits 2). Startup errors that carry an upstream message (handshake, `tools/list`) are printed with control characters escaped. Rules in `docs/specs/profile-schema.md` section 8.4.

### Changed

- Release setup for the first tag, v0.1.0: the GitHub release page is `docs/releases/<tag>.md`, written in the release pull request from this file, instead of GoReleaser's list of every commit, and `release.yaml` stops before building when the file is missing or empty. The Homebrew formula is generated but not uploaded (`skip_upload: true`) until `fathomgate/homebrew-tap` and its token exist, and the container image is built but not pushed (`skip_push: true`) until it is multi-arch, tagged `vX.Y.Z`, `vX.Y` and `latest`, and signed; `release.yaml` drops `packages: write` until then. `checksums.txt` is signed with cosign keyless (Sigstore): GoReleaser `signs:` runs `cosign sign-blob --bundle` and the release carries `checksums.txt.sigstore.json`, whose certificate names `.github/workflows/release.yaml` at the tag. `release.yaml` installs cosign v3.1.3 through `sigstore/cosign-installer` v4.1.2 (SHA-pinned) and grants `id-token: write` to the `goreleaser` job only; no workflow a pull request can start has it, and `snapshot.yaml` still skips signing. That job runs no test or dependency code: a new unprivileged `test` job (`contents: read`) runs `go test`, the `go mod tidy` diff check, `make vulncheck` and `make licences-check`, and GoReleaser runs with `--skip=before` after it. Both checkouts use `persist-credentials: false`; the registry login, QEMU and the tap token are gone until the image and the tap are published; the tag must match `vX.Y.Z[-pre]` and the notes are passed from a fixed path (security review of #119). docs/install.md and the release notes give the `cosign verify-blob` command, pinned to the workflow at the tag, the GitHub OIDC issuer and the `push` trigger. ### Security

- `fathomgate serve --listen` binds both loopback families on its port (T0.52; H1 in the post-merge security review of PR #109; [ADR 0023](docs/adr/0023-listener-binds-both-loopback-families.md), accepted). `--listen localhost:P` or `127.0.0.1:P` bound only `127.0.0.1:P`, so another local user could bind `[::1]:P` and receive the bearer token of an agent configured with `http://localhost:P/mcp` that tried `::1` first; `[::1]:P` had the reverse gap. fathomgate now binds the address asked for and then the other family's loopback on the same port, serves both, and logs one `listening url=...` line for each. If the other address is taken, it exits 1 before the upstream starts, naming the address; with port `0` it retries on a new port; a host without that family logs a warning and serves on one. `--listen` now takes only `localhost`, `127.0.0.1` or `[::1]`: another `127.0.0.0/8` address, bound alone, left `127.0.0.1` and `[::1]` on its port to other users, and exits 2. A new connection must deliver its first request's headers within 3 seconds (L1); the 128-connection cap is shared by both addresses. The install guide says to paste the exact URL from a `listening` line and to restart fathomgate at once when it stops (port squatting while it is down is open until M1).
- Token files, the audit signing key and the audit log with a macOS extended ACL are refused (T0.52, L2). The owner-only checks read the mode bits, which do not show an ACL entry such as `everyone allow read` set with `chmod +a` or inherited from the folder. `internal/fileacl` reads the ACL with `fgetattrlist(2)` on the open file, without cgo; CI runs the tests with real ACLs on `macos-latest`.
- A launcher's server no longer outlives its upstream (T0.46, [ADR 0021](docs/adr/0021-kill-the-upstream-process-tree.md); S2 in the security review of PR #77). A stdio upstream now starts in a process group of its own on Linux and macOS (`Setpgid`) and in a Job Object of its own on Windows (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, no breakaway), so the server behind `uvx`, `npx`, `uv run` or a shell script is part of the upstream's tree. On Windows the upstream is created suspended, assigned to its job and then resumed, so nothing it starts can run outside the job; if the job cannot be created, assigned or resumed, the upstream is killed and startup fails. The ADR 0018 restart, every failed startup attempt and the startup budget running out now kill the whole tree (`SIGKILL` to the group, or `TerminateJobObject`), so the first copy of the server no longer keeps running, with the `--upstream-env-pass` credentials in its environment, beside the second. Startup now meets its 30-second budget on those paths instead of overrunning it by up to 2 seconds (the `exec.Cmd` `WaitDelay`, which stays as a backstop). On shutdown the group gets `SIGTERM` and `SIGKILL` 250 ms after go-sdk sends each to the upstream (5 and 10 seconds after its stdin closes), and on Windows the job is terminated when go-sdk kills the upstream. Once the upstream has been reaped, on shutdown and when it exits mid-session, what is left of its tree is swept once: `SIGTERM`, up to 2 seconds, then `SIGKILL` (only `SIGKILL`, with no wait, when the group has already been sent it); the job is terminated on Windows. On Windows the tree also dies if fathomgate itself crashes. The first `EPERM` on a group signal (a setuid launcher) is logged at Warn. This is containment, not a sandbox. Residuals: a descendant that calls `setsid()` or `setpgid()` leaves the group on Unix; on Windows any descendant can start a process outside the job by naming a same-user process outside the job, fathomgate included, as its parent, or through a service; a setuid launcher's member may not be signalled; a container behind `docker run -i` is never in the tree; fathomgate as PID 1 in a container needs `docker run --init`; a fathomgate crash on Unix still orphans the tree (run it under systemd); an upstream that reads the controlling terminal is stopped (`SIGTTIN`) in an interactive shell. `internal/proxy` imports `golang.org/x/sys/windows` on Windows (ADR 0011 amendment row); `CGO_ENABLED=0` still holds. New CI job `go test (macos)` runs `go vet ./...`, `go test ./...` and `go test -race ./internal/proxy/` on `macos-latest`; it is not a required check yet.
- The install guide now requires netdev-ssh-mcp v1.7.1 (T0.51). v1.6.6 and earlier leave some secrets in clear or reversible ([GHSA-8g43-jrf3-q9vq](https://github.com/krisiasty/netdev-ssh-mcp/security/advisories/GHSA-8g43-jrf3-q9vq), fixed in v1.7.0, reported by Fathomgate in T0.29), and v1.7.0 and earlier let a tool call make the device run further commands ([GHSA-h47r-329w-6p9h](https://github.com/krisiasty/netdev-ssh-mcp/security/advisories/GHSA-h47r-329w-6p9h), fixed in v1.7.1). Upgrade if you followed the earlier guide. The guide keeps the upstream's default per-run obfuscation key and presents a key file as optional, kept where the agent's tools cannot read it.
- A tool call that arrives over the HTTP listener can no longer be read as the local stdio agent's if go-sdk stops copying the HTTP request into the call (T0.31; L1 in the security review of T0.48). The listener marks the context of every authenticated request, `transportOf` reads the mark as `http`, and a call that reads as `http` with no principal is refused with `fathomgate refused <server>.<tool>: the request arrived over the HTTP listener without an authenticated principal` before anything is keyed or forwarded. `fathomgate serve` also never runs the stdio agent and the listener in one process.
- An MRTR `requestState` is bound to the agent side it was issued to (T0.30, ADR 0016). fathomgate now issues sealed envelopes (then `ng3.`, `fg4.` since the rename) whose AES-GCM additional authenticated data is the transport (`stdio` or `http`) and the principal (the listen token's name; empty on stdio), so a retry from another principal or over another transport is refused with `-32602` `invalid_request_state` and the same detail as a forged envelope, naming neither side, and nothing reaches the upstream. `ng2.` envelopes from before the upgrade could never open (the key is per process) and now get `requestState was issued by an earlier fathomgate process; call the tool again without it`. A refused `requestState` is logged at Warn with the presenting transport and principal, rate-limited. The call `Proxy.dispatch` receives carries the transport beside the principal; a principal remains attribution only. Each progress mapping belongs to its one agent request through a token that is fresh for that request and never shared by two. profile-schema 8.4 states the cross-session attribution rule.
- A same-principal MRTR retry that keeps a valid `requestState` but changes the tool or the arguments is now logged at Warn, like a state that does not verify (T0.48, L2 in the post-merge security review of PR #85). It was refused with `-32602` and nothing reached the upstream, but no line recorded it. The line names the presenting transport and principal, the server and the tool the retry was presented on, and fathomgate's own reason (`requestState was issued for another tool` or `arguments differ from the call that asked for input`); it quotes no argument and nothing from the envelope. It shares the refusal rate limiter, keyed by server, transport, principal and reason. The progress relay no longer carries the session key, transport and principal fields T0.30 added: nothing read them, and the per-request guarantee is the upstream token, which is now drawn only in `watchProgress` (L1). ADR 0016 amendment row, profile-schema 8.2 and 8.4 and the threat-model rows "Progress token scope" and "Cross-principal `requestState` replay" say so; the latter now states the 30-minute same-token replay residual in full, and the stdio-side one: a listener call with no go-sdk `Extra` would bind as the local agent's `{stdio, ""}`, safe only while `fathomgate serve` keeps the two sides exclusive (T0.31 must fix or re-state it).
- One principal can no longer hold every other principal's stateful upstream prompts in refusal without a trace (T0.44, S2 and S4 in the post-merge security review of T0.40). Every stateless per-request call, and every session past 1024 per upstream, used to share one orphan entry that was foreign to every session and never pruned, logged or attributed. Now each call fathomgate cannot name to a session gets an orphan key of its own (`r` and a per-proxy counter; a stateless agent's session is never keyed by an id), so its ended call is an ordinary record: pruned at `OrphanTTL` and logged at Info with its principal when reaped. Each refusal of an upstream prompt is logged at Warn with the principals behind it (`ended_calls_of`, `in_flight_of`, or the attributed call's `principal`), at most once per 10 seconds per server, attribution, class and principal set, with a `suppressed` count (and `suppressed_lost` when the limiter's table is swept). The 1024-entry table cap is now a quota of 256 records per principal per upstream. Past it, that principal's further ended calls fold into one overflow record of its own, which fails closed, refuses that principal's own sessions' prompts too, is logged at Warn when made (expected for a 2026-era agent above about 0.85 calls a second to one upstream) and at Info when reaped, and cannot push another principal's records out. The residual is accepted by the maintainer (2026-09-24): a principal that keeps ending calls, or holds one open, on a stateful upstream keeps other sessions' prompts on it refused while it does; the only recourse is removing its token. M3 needs a per-upstream prompt policy or principal binding (new Open threat-model row).
- A stateful upstream's prompt refused by the orphan rule can no longer put fathomgate's text in place of the upstream's own error (T0.42, S3 in the post-merge security review of T0.40). When the one call in flight could not have been prompted anyway (ADR 0014, or no form elicitation), fathomgate recorded the refusal as that call's own, and an upstream error for the call was then replaced by it, although the prompt was exactly one fathomgate could not attribute to that call; a hostile upstream could trigger this at will and speak in fathomgate's voice about why a call failed. The refusal is now a note on that call only: appended to a result the upstream completes, never in place of an upstream error or result, which is what SECURITY.md promised. Over the HTTP listener a 2026-era agent calling a 2025-era upstream that fails the call now gets the upstream's error, which may quote the ADR 0014 refusal (a go-sdk upstream does), instead of fathomgate's tool error. Test `TestOrphanRefusalNeverReplacesUpstreamError`.
- The local stdio agent is keyed as its own session whether or not an HTTP handler has been built (T0.43, S1). The key came from whether the proxy had a listener: once `HTTPHandler` had run, the stdio session (which has no session id) was keyed into the shared orphan entry, and after its first call no stateful upstream prompt reached anyone on that upstream for `OrphanTTL`, renewed by its own traffic. Latent until `--listen` (T0.31). `Proxy.Run` now records the session it serves and gives it a key of its own (`l1`, `l2` for a second `Run` on one proxy, which only tests do), so two agents on one proxy never share a key either. A request on the local session that go-sdk dispatches while `Run` is still connecting waits for that record without any lock held across the connect, and gets the shared entry only if its context ends first; a call over the HTTP listener never waits (it is keyed by its session id or gets the shared entry). Tests `TestListenerCallNeverWaitsForRun`. `Run` wraps a connect failure as `proxy: connect agent session: ...`. Tests `TestLocalAgentOwnOrphanWithListener`, `TestLocalKeyDuringConnect`, `TestAgentSessionKey`; `TestProgressStuckAgent` and `TestEndBeforeFinish` now expect the orphan refusal between their two in-process agents before the orphan expires.
- The documented residual of the orphan rule is corrected (T0.44, doc part; S2 and S4): the shared orphan entry (every stateless per-request session, and every session past 1024) is not pruned, not logged and not attributed to a principal yet, so a refusal it causes cannot be explained from the log, and "up to `OrphanTTL`" bounds one ended call, not the steady state: one principal can keep every other principal's stateful prompts refused on an upstream with one stateless request per `OrphanTTL`. This is recorded as **open**, not accepted: its own threat-model row ("Cross-principal refusal of stateful prompts via the shared orphan entry", owner mcp-protocol-engineer), T0.44, which must land before `--listen` (T0.31). The code fix needs a maintainer's choice. The residuals also state that which refusal an agent sees reveals whether another session ended a call on that upstream within `OrphanTTL`.

- A stateful upstream's prompt that arrives after its call finished **normally** no longer reaches another agent session's human (T0.40, J1 in the re-review of PR #72). fathomgate remembered only cancelled calls, so a call the upstream had answered left nothing behind; an upstream that kept working on it in the background, or whose prompt go-sdk dispatched after its result, could then have that prompt attributed to whichever other session had a call in flight, and that human's answer went back as the answer to the first call (confused deputy, MCP03). Every call that ends is now remembered as an orphan of its agent session, cancelled or not, and a prompt is relayed only when the one call in flight and every live orphan on that upstream belong to one session. That window is its own option, `HTTPOptions.OrphanTTL`, **5 minutes** by default instead of the 30-minute idle `SessionTimeout` it used to borrow (J3), and reaping an orphan is logged at Info with the server and the principal it was blocking for. Where the one call in flight could not have been shown any prompt anyway (a stateless agent, ADR 0014), the refusal still says so. Accepted residual: with more than one agent session on one upstream, a stateful upstream's prompt is refused for up to 5 minutes after any other session's call ends. Tests `TestHTTPPromptAfterFinishedCall`, `TestOrphanTTLSeparateFromIdle`, `TestOrphanReapedLogsPrincipal`, `TestAgentSessionKey`; rules in `docs/specs/profile-schema.md` sections 8.4 and 8.5; threat-model row "Stateful upstream prompt for a call that ended normally".
- `fathomgate serve` no longer echoes an argument that could be a password (T0.23, ADR 0017, security review of #64): a stray positional (`--upstream-env DEVICE_PASSWORD FAKE-x` put the password there), an unknown flag (`-FAKEx`), bad flag syntax, a malformed `--upstream-env` argument and a bad key are all reported by position only (`unexpected argument N; ...`, `unknown flag at argument N`, `--upstream-env argument N: key must match ...`); the flag package's own messages are discarded, and a reserved flag after `--` is named without its `=value`. `--upstream-env FATHOMGATE_*=...` is now refused with exit 2 (ASCII case-insensitive on Windows), as `--upstream-env-pass FATHOMGATE_*` is, so neither flag can hand an upstream fathomgate's own settings. Canary tests cover every error path. Accepted residual: a value typed where a name belongs is named by the `--upstream-env-pass` "not set" error.
- A slow agent can no longer stall an upstream through the progress relay (T0.28, security review S2 on PR #53). go-sdk dispatches an upstream's notifications and requests one at a time, and the relay wrote each progress notification to the agent on that goroutine while holding the call's lock. An agent that stopped reading therefore held up every later message from that upstream, another call's `elicitation/create` included. When the call's result then arrived, its end waited on the stalled write and left a stale in-flight entry, which broke the attribution of a stateful upstream's prompts. The relay now only queues. One sender goroutine per call writes to the agent from a queue of at most 10 (when the queue is full the newest entry is replaced, so progress still increases). At the end of a call fathomgate waits at most 1 second for the queue to be written, then drops the rest and releases the call. Nothing follows the result. A notification the rate limit held back is now sent as soon as a rate slot frees up, not only before the result (S4). Rules in `docs/specs/profile-schema.md` section 8.4, "Delivery"; threat-model row "Upstream notification queue blocked by a slow agent" is now mitigated.

The CI `golangci-lint` job runs `make lint` in place of the action, with `persist-credentials: false` and `make toolchain-check`. The local fallback to `go vet` when golangci-lint was not installed is gone, and `make lint` type-checks for `linux/amd64` under the `go.mod` toolchain, as CI does. The reasons are in `CONTRIBUTING.md`.

- The audit checkpoint private key and the audit log are owner-only on every OS (T0.12). `audit.SaveKey` (and so `fathomgate audit keygen`) creates the key exclusively and never overwrites an existing file or symlink. On Unix it uses `O_EXCL` and `Chmod(0600)` on the descriptor, so `keygen --out` onto an existing `0644` file is refused instead of leaving the key world-readable. On Windows, where `0600` did nothing and the key inherited its folder's ACL (for example `BUILTIN\Users` read under `C:\ProgramData`), it is created by `CreateFile` with a protected DACL granting only the current user and `SYSTEM`, so a local non-admin user can no longer read the key and re-sign checkpoints over a rewritten log. `audit.NewWriter` creates a new log the same way and never truncates. An existing log is opened without following links and refused unless it is a regular file with one link (no symlink, junction, reparse point or hard link) owned by the current user, so a writer running as root or SYSTEM can no longer be pointed at another file and change its permissions. The chain is verified through the held handle, and only then is the log reset to owner-only (mode `0600` or the protected DACL), which strips any read access granted to a log shipper. On Windows every new key, public key and log is created with `FILE_FLAG_OPEN_REPARSE_POINT`, so a dangling symlink planted at the path cannot redirect where the file is created. `keygen` also refuses an existing `<out>.pub`, writes the public key first through the new `audit.WriteKeyPair`, and deletes it again if the private key fails; partial files are deleted through their handle. The interim `icacls` guidance in `SECURITY.md` is replaced by what the code guarantees.
