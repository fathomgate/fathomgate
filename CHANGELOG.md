# Changelog

All notable changes to Fathomgate are recorded here. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html) from `0.1.0`. Until `1.0.0`, a minor version may change the policy or profile file format, with a migration note.

Entries use the project vocabulary: decisions are allow, hold, deny, expired; classes are spelled as in [docs/glossary.md](docs/glossary.md).

- Example policy cases for M1 test-matrix rows 3, 4 and 6 (M1-21): `show ip bgp summary` allowed by `reads-anywhere` (directly and after the downgrade), `reload` denied by `no-exec` through netdev-ssh-mcp `run_show_command`, upa `send_command_and_get_output` and eos-mcp `run_command`, and an unknown host denied by `default:unknown_target` for writes and exec. The three suites now hold 45 cases (read-only 12, lab-open 13, prod-approval 20). A test case takes its class as given and cannot carry a command, so the classification half of each row stays with the tier 1 tests in `internal/classify`.
- `internal/gate` (M1-18, ADR 0026): the library the proxy will call at `Proxy.dispatch` (wiring is M1-19). For one `tools/call` it parses the arguments, takes the targets exactly as the upstream receives them, classifies (annotations can only raise a read tool to `EXEC_ARBITRARY`, `class_source: annotation_raise`, and a raised tool is never downgraded), resolves each target, runs `policy.Evaluate` with the session counters the proxy passes in, and returns a `seam.Verdict`: forward or not, the one-line tool error `fathomgate <denied|cannot run|held> <server>.<tool>: rule <rule_id> (class <CLASS>): <reason>`, and the fields of the Info decision log line (`decision`, `session_id`, agent and upstream protocol and era separately, no argument value; the trace is resolved only at Debug). `seam.CallInfo` and `seam.Verdict` live in `internal/gate/seam`, which imports nothing from fathomgate (ADR 0026 amendment). A `hold` is not forwarded and gets the fixed text "needs approval, and approvals aren't available yet, so this call was not run."; an `allow` is forwarded only when its obligations are among `redact`, `notify`, `require_ticket` and `canary_first` (otherwise `cannot run`). The tool error never quotes a target, command or upstream text; `default:` rules get fixed text. New reserved rule id `default:bad_arguments` (`policy.RuleBadArguments`, policy-schema section 5) for arguments that are not one JSON object (or repeat a key, or are not UTF-8), a target that is not a hostname or IP literal, a tool that reaches devices called with no target or with a tag or group selector (profile-schema section 2.2), a tool the profile does not list called with any argument, and, once M1-35 lands, an argument the profile does not name or a malformed one. Benchmark: about 5 µs per call over a mixed corpus.
- The gate is wired into the proxy (M1-19, ADR 0026). `proxy.Options.Gate` (an interface over `internal/gate/seam`, implemented by `*gate.Gate`) decides every `tools/call` at `Proxy.dispatch`, MRTR retries included, before anything reaches the upstream; a `deny`, a `hold` and an `allow` whose obligations cannot be met are the gate's one-line tool error (`isError: true`), and no upstream call is made. A forwarded call carries the arguments object re-encoded from the one the gate checked, never the agent's bytes. Arguments over 64 KiB are denied with `default:bad_arguments` before the gate runs; a gate that panics is denied with the new reserved id `default:internal_error`. Session counters (`devices_touched`, distinct devices, only calls the gate allows) are kept per principal over HTTP, in both eras, and per process on stdio (ADR 0026 decision 4 as amended by the maintainer 2026-09-25), under one lock per key taken with the call's context. A retry whose `requestState` does not verify, or a call to an upstream that has exited, is refused before the gate runs. One Info `msg=decision` line per call, with the trace at Debug. `readOnlyHint` is read from the upstream's raw `tools/list` answers so an absent hint is never taken as `false`; `destructiveHint` maps directly. `tools/list` advertises only the arguments a tool's profile names, with `additionalProperties: false` (ADR 0033 section 4). `readOnlyHint` keys are matched exactly, as go-sdk matches them. The proxy's own refusals carry `class_source` `proxy`. With a policy, an upstream prompt during a call to a tool whose server has a profile is refused, since its answer would be an argument the profile never named (ADR 0014 note). With no gate, `serve` stays pass-through; M1-20 adds `--policy`. `internal/gate` reads `classify.Result.UnnamedArgs` and `MalformedArgs` directly and gains `Arguments(server, tool)`.
- Tier 1 overhead budget tests (M1-23, PRD M1 metric). `TestDecideOverhead` and `TestDispatchOverhead` time every call through the real gate, with the repo profiles, `prod-approval.yaml` and `inventory.example.yaml`, alone and on the proxy's dispatch path. They fail when the p99 of the typical corpus is over 5 ms (10 times that under `-race`). Worst cases at the 64 KiB argument cap are checked one by one at p50, with their p99 logged. On a GitHub-hosted Linux runner the typical p99 is 33 µs for the gate and 131 µs for the proxy's decision stage. Two findings are recorded in `gatetest.KnownOverBudget` and `docs/testing/test-strategy.md`: 1,900 commands in one call take 10 to 21 ms, because each is matched against backtracking regexps and the proxy runs `Decide` twice when a target is already counted, and 3,300 targets take 9 ms in the proxy. The Linux, Windows and macOS CI jobs run both tests alone, at 1x, with `-p 1` and `FATHOMGATE_OVERHEAD_STRICT=1`, which also times and enforces each worst case's p50 (a known case fails once under 0.8 of the limit, so its entry comes out); every other run checks the worst cases' verdicts only. `internal/proxy`: the decision stage of `gated` is extracted, unchanged, as `decideAndRespond`, the unit the proxy test times.

- `fathomgate serve --policy <file> [--inventory <file>] [--profiles <dir>]` (M1-20, ADR 0027). The policy, the static inventory and the profiles are loaded and checked before anything is bound or spawned; any file that does not load exits 2 and no upstream starts. The shipped profiles are built into the binary (`profiles/embed.go`, `go:embed`), so a release binary needs no files beside it, and `fathomgate version` lists them (server key, tool count, the first 12 hex digits of each file's SHA-256). `--profiles <dir>` replaces the built-in set; it never merges with it. `--inventory` takes `inventory.yaml` (a CSV is refused with a pointer to `fathomgate inventory import`). The start-up line names the policy file and its rule count, the inventory and its device count, the profile source and the profile file for `--server`. Each of `--policy`, `--inventory` and `--profiles` may be given once. Profile files are named after their server key (`profiles/upa.yaml`). Warnings at start: no `--inventory`, a server with no profile (every call with arguments is denied, below), an explicit `unknown_target: allow` (ADR 0032), a hostname pattern that matches no listed device (ADR 0031, new `inventory.File.PatternWarnings`), each obligation on an `allow` rule that M1 does not enforce or cannot meet, with its rules, and the `hold` rules, which are not run until M3. `--audit` is still refused, and now says it arrives in M4.
- `fathomgate inventory lint <file>` and `fathomgate inventory resolve [--inventory file] [--json] <name>...` (M1-34, ADR 0031, inventory-schema section 9). Both read the file as `serve --inventory` does (a `.csv` is refused; owner, write-permission and size checks of `internal/configfile`). `lint` checks everything a load checks and fails on a hostname pattern that matches no listed device, which `serve` only warns about, and on a listed device whose name the gate refuses as a target; it warns for every role, site or tag a pattern adds to a listed device, naming the device's own role where a pattern adds a tag to it. `resolve` prints whether each name is known exactly as `serve` counts it, the provider that listed it and which provider supplied each field and tag (`static` or `pattern`); for an unknown name it says why and which patterns it matches; a value that is not printable ASCII is printed quoted. `inventory.Known` is the one exact-name rule, used by the gate, `policy eval` and `resolve`. `inventory.Target` gains `Source`, `Sources` (per field) and `Stale`, set by the chain and refused in a file.
- GitHub issues follow the board automatically (M1-38). `tools/status/issues.py` gives each task's issue exactly one `state:` label matching `docs/milestones/*.yaml`, plus its `milestone:` and `agent:` labels, and closes the issue of a merged or validated task as completed and of a dropped task as not planned, with a one-line comment naming the PR. It prints a drift report: issues for task ids on no board, active tasks with no issue, and open issues with no activity in 30 days. It is a dry run unless given `--apply`. It stops before changing anything if a label is not defined in `.github/labels.yml` or a task id is on two boards; it closes nothing and fails if more than `--max-close` issues (default 5) would close, and with `--since <sha>` it closes only tasks whose state changed since that commit. Only issues opened by an owner, member or collaborator are managed; title any other issue about a task differently (`Follow-up to M1-22: …`). `.github/workflows/issue-hygiene.yaml` runs it with `--apply` on a push to `main` that changes the board (closing only what that push changed), weekly and by hand (with a `max_close` input), never on a pull request, and puts the drift report in the job summary; `/status` runs the dry run.
- Per-call caps in the gate (M1-39): a call with more than 64 commands, or more than 256 target names and group selectors, is denied with `default:bad_arguments` before it is classified (`a call may carry at most 64 commands; split it into smaller calls`, `a call may name at most 256 targets; split it into smaller calls`; `parse_error` `too_many_commands` or `too_many_targets` in the decision line). Profile-schema section 2.4 gives the counting and why the numbers: 64 commands of the classifier's 1 KiB fill the 64 KiB argument cap, and 256 is five times the largest shipped `max_devices`. The command blocklist and the shell-metacharacter check run without regular expressions (same answers, checked by fuzz tests against the old expressions; about 11 times faster on a long command), and the proxy decides each call once instead of twice when a target is already counted (`seam.CallInfo.Counted`, ADR 0026 note). The worst cases at the 64 KiB argument cap now take about 1 ms at p50 in `Decide` and in the proxy's decision stage, down from 5.5 to 18 ms, and `gatetest.KnownOverBudget` is empty.

- Capability tables for meta-tools (M1-17, ADR 0010, profile-schema section 2.5, test-matrix row 18). A profile may now carry a top-level `capabilities` map of tables, each mapping a capability id to a class, and a tool may name one with `capability_table` and the argument that picks the operation with `capability_param`. The id is looked up byte for byte; a listed id gives the table's class, and anything else (an unlisted, missing, `null` or non-string id, a case variant, a padded or look-alike id) is `EXEC_ARBITRARY`, always with `class_source: capability_table`, which `Classify` now emits. The loader requires a meta-tool's own class to be `EXEC_ARBITRARY`, refuses command or config arguments on it, and accepts only printable-ASCII table keys with no two differing only in case. `capability_param` is in the closed argument list's named set and must be one string. The gate applies the annotation raise to the table's class, so `readOnlyHint: false` on a meta-tool raises a listed read, and `readOnlyHint: true` never lowers an unlisted id. New profile `profiles/cisco-meraki-mcp-official.yaml` for the official Cisco Meraki server at `c1d00ea`: `semantic_search` is `INVENTORY_READ`, and `execute_api` classifies from a 493-row table covering every GET operation the upstream indexes (`configure` operations `READ_CONFIG`, `monitor` and `liveTools` `READ_OPERATIONAL`, with eight exceptions in the profile header; `getNetwork` and `getOrganizationNetworks` stay `READ_CONFIG` because they carry the Systems Manager `enrollmentString`). Its `parameters` argument is refused under ADR 0033, so only the four capabilities that need no parameter can run through fathomgate until a decision record covers it (moved to M2 by the maintainer 2026-09-25). A malformed capability argument gets its own deny reason, `the capability argument must be one string that does not parse as JSON`. Tier 1 fixture `tests/fixtures/meraki/` (the upstream's own `tools/list` and capability set, generated from its code by `generate.py`), with table, fuzz and gate tests and a threat-model row for capability-id spoofing.

### Changed

- `fathomgate policy eval` reads `--profile` and `--inventory` as `serve` reads a profile and an inventory (M1-33, security review of PR #197): the owner and write-permission checks, the 16 MiB cap, a profile file named after its server key, and no CSV. A file others can change is now a usage error (exit 2) for `eval` too. Its output labels are padded to one width.
- In a `*.test.yaml` gate case, an unquoted value in `arguments` must reach the gate as written (M1-33, security review of PR #197, L4): `0x1F`, `017`, `+5`, `1_000`, `True` and `~`, and numbers whose JSON is not their text (`1.0`, `2.50`, `-0`, a long `3.14159...`), are load errors that name the line; quote the value, or give the bytes in `arguments_json`. Plain strings that look like a number, a date or a time (`1e3`, `2026-09-25`, `12:30`, `65000:100`, an all-digit MAC address or IPv6 literal) are load errors that say to quote them (R3 of the re-review of PR #199). A test file may not use YAML anchors or aliases, a case name is at most 256 bytes, and a test file and its policy are read through a 16 MiB cap (L3).
- `fathomgate policy eval --profile` decides through `internal/gate`, as `serve --policy` does (M1-33, ADR 0035), so it now applies the parse checks, the per-call caps, the group-selector and zero-target refusals that it used to skip. With `--profile`, `--class` and `--target` are usage errors (exit 2; `--class` used to override the profile's class silently), `--server` must be the profile's key, and `--arg` and `--arguments-json` are only accepted with `--profile`.
- The `*.test.yaml` runner moved from `internal/policy` to the new `internal/policytest`, and the profile-set and inventory loading `serve` does moved to the new `internal/configset`, which `serve`, `policy test` and `inventory lint` and `resolve` share (M1-33, ADR 0035). `internal/gate` gains `Explain`, which returns `Decide`'s verdict with the operator's detail.
- **Breaking: `fathomgate serve` needs `--policy <file>` or `--no-policy`** (M1-20, [ADR 0027](docs/adr/0027-serve-policy-inventory-profiles-flags.md)). With neither it exits 2 before starting the upstream, and the message names both flags. `--policy` decides every call with that policy file; `--no-policy` keeps v0.1.0's pass-through, forwarding every call unchecked, and logs a warning at every start. Upgrade: add `--policy <file> --inventory <file>`, and check that `--server` is a server key that `fathomgate version` lists (for example `netdev-ssh-mcp`). A `--server` name with no profile denies every call that carries arguments. Or add `--no-policy` to keep v0.1.0's pass-through. The policy and inventory files must not be writable by other users. `fathomgate version` now prints more lines: the embedded profiles follow the version line. `docs/install.md` has an *Upgrading from v0.1.0* section.

### Security

- Text from a file no longer reaches the terminal raw through `fathomgate` errors, and no value a parser echoes can forge an output line (M1-33, security reviews of PR #197, L1, and PR #199, R1). A new `internal/termsafe` is the one quoting helper of the CLI and the policy test runner; every CLI error (including `serve` and `inventory lint`) is printed on one line through `termsafe.Text`, which escapes every C0 control (line feed and tab included), DEL, C1 controls, U+2028, U+2029 and the bidirectional formatting characters; the file-permission fix commands are printed after it on lines of their own (`configfile.Hint`); paths from a test file, a profile directory or an inventory, an invalid hostname pattern and a profile's server key and tool names are quoted where they enter a message; and `internal/configfile` no longer repeats the raw path an operating-system error carries.
- A `*.test.yaml` file can no longer expand without bound through YAML aliases (M1-33, security review of PR #197, L3: a 425 KB file took 40 s and printed 600 MB).
- `fathomgate serve` refuses a hybrid upstream at startup (M1-32, ADR 0008 amendment; security review of PR #151). An upstream that answers the `initialize` request with a later protocol version than fathomgate asked for (2026-07-28 to a 2025-11-25 request, after go-sdk's own fallback or the ADR 0018 restart) used to be accepted and labelled `era=stateful`, while go-sdk added the stateless `_meta` self-description to requests on a session with a handshake. Now the session is closed before `notifications/initialized`, the upstream's process tree is killed at once and `serve` exits 1 with an error naming both versions and ADR 0008. No flag. go-sdk, TypeScript and Python SDK servers are not affected. Rules in `docs/specs/profile-schema.md` section 8.4.
- A server-initiated `elicitation/create` from an upstream fathomgate connected with `server/discover` (the stateless era) is refused, with or without a policy and whether or not the server has a profile (M1-32, ADR 0008 amendment; F1 in the security review of PR #151). go-sdk's client accepts one in either era and fathomgate used to relay it; M1-19 refused it only for a profiled server under a policy. The upstream gets a JSON-RPC error and the agent a refusal naming the reason and ADR 0008; the prompt is not shown. MRTR `input_required` from such an upstream is relayed as before. Rules in `docs/specs/profile-schema.md` sections 8.2 and 8.4.
- Answers to upstream prompts no longer reach an upstream unchecked once a policy is loaded (M1-19, PR #167; security review of PR #161, N1; ADR 0014 note, accepted by the maintainer 2026-09-25). An upstream that asks the agent for input mid-call (junos-mcp-server v1.1.1 `add_device` elicits `ssh_key_path`) got a second argument channel the closed argument list never checks. With a gate set, fathomgate refuses every upstream input request, `input_required` and `elicitation/create`, during a call to a tool whose server has a profile, and never shows the prompt. With `--no-policy`, or for a server with no profile, prompts are relayed as in 0.1.0.
- `max_devices` can no longer be reset by session churn (M1-19, PR #167, security review M1): over HTTP it is counted per principal for both eras, so closing, reopening or having a session evicted keeps the count, and mixing eras does not double it.
- Target names are matched exactly at the gate (M1-18, from the security reviews of PR #152, #154 and #158). `internal/gate` refuses with `default:bad_arguments` a target that is not a hostname or IP literal (`lab-x@core-rtr-01`, leading or trailing space, control characters, non-ASCII look-alikes, `:` outside IPv6, `-oProxyCommand=...`, inet_aton spellings such as `127.1`), a comma inside a single-target argument, and an eos-mcp `daily_brief` or `*_batch` call with no `hostnames` or with `tags` (the upstream would run on its whole fleet, or on a tag it expands itself, while fathomgate counted zero devices). A name is known only when an inventory record carries exactly that string and did not come from a hostname pattern alone (ADR 0031), so `CORE-rtr-01` and `core-x.attacker.example` are `unknown` even with `^core-` active.
- `internal/classify` no longer downgrades a multi-line command (M1-16, from the security review of PR #150). Whitespace collapsing turned line breaks into spaces, so `show clock\nconf t\nhostname pwned\nend`, `show clock\ncopy run start`, `show clock\nrelo\n\nshow clock` and `show clock\ntclsh` through a free-form tool were `READ_OPERATIONAL` and allowed by `reads-anywhere`, while netmiko sent every line to the device. A command with any control character other than tab (newline, carriage return, vertical tab, form feed, NUL, Ctrl-C, Ctrl-Z, escape, DEL) or any non-ASCII byte (NEL, U+2028, U+2029, C1 controls, no-break and zero-width spaces, look-alikes) is now `EXEC_ARBITRARY`, checked before whitespace is collapsed; tabs still collapse like spaces. So is any word after the first that starts with `-` (option injection into `ping` or `traceroute` on the server host). The blocklist gains classification.md section 5.3's start-anchored verbs and the abbreviations device CLIs accept anywhere in the line (`conf t`, `wr`, `rel`, `relo`, `copy`, `tclsh`, `bash`, `python`, `guestshell`, `start shell`, `undebug`), and `monitor` is allowed only as `monitor traffic` with a bounded `count`, with `write-file` and `read-file` blocked.
- Config dumps given in short form are `READ_CONFIG`, not `READ_OPERATIONAL` (security reviews of PR #150 and PR #152, high). The second word of `show`, `display` or `get` is a config read when it is a prefix of a config keyword (`running-config`, `startup-config`, `configuration`, `tech-support`, `derived-config`, `archive`, ...) or the keyword is a prefix of it, and likewise the third word after an abbreviation of `system` (`rollback`, `configuration`, `admin`, `interface`, `ha`). So `show ru`, `show tec`, `show derived`, Junos `show sys rol 1` (the previous configuration with `$9$` secrets) and a bare `show`, `get` or `display` (FortiOS prints the whole configuration) are `READ_CONFIG`.
- The downgrade also refuses `"`, `'`, backslash, `{`, `}` and `$`, which a shell on the server host turns into an option (`ping 1.1.1.1 "-f"`, `ping {-f,1.1.1.1}`, `${IFS}`); commands longer than 1024 bytes; and Junos `monitor traffic` without `count`. `Normalize` trims commands of spaces and tabs only and keeps empty elements, so `show version` with a trailing newline and `["show version", "\n"]` are `EXEC_ARBITRARY`. The `never-downgrade` token is matched case-insensitively (`Never-Downgrade` downgraded before). `Result.Reason` no longer quotes the command or the tool name.
- NX-OS `show file bootflash:backup.cfg` and `show diff rollback-patch checkpoint cp1 running-config` are `READ_CONFIG` (`file` and `diff` are config keywords; `show file systems` over-matches, accepted). The downgrade also refuses `*`, `?`, `[`, `]` and `~`, and allows a `$` only at the end of a word, so IOS `show ip bgp regexp _65000$` passes while `$HOME`, `${IFS}`, `$'...'` and `$(...)` stay refused. `monitor traffic` needs a `count`, and every `count` must be followed by `n` from 1 to 1000 (so `count 5 count 999999` fails in either order), and Junos `monitor interface`, which takes no count and runs until interrupted, is no longer allowed (security and Go re-reviews of PR #152).
- Known and accepted: a FortiOS `show` whose second word is not a config keyword (`show vpn ipsec phase1-interface`, `show user local`) is still `READ_OPERATIONAL`, because the classifier does not know the vendor; M2 redaction must run on every result, whatever the class (classification.md section 2, threat model).
- `inventory.example.yaml` ships no active hostname pattern and lists every device by name (security review of PR #154, H1 and H2). A pattern resolves any name the agent sends, and any match makes the name a known device. With the previous patterns (`^core-|^border-`, `^lab-` with `tags: [lab]`, `^fw-`; case-insensitive, not end-anchored), `core-x.attacker.example`, `lab-x.attacker.example` and `fw-evil.example` were `allow reads-anywhere` for `READ_CONFIG` under all three example policies. A free-form-host upstream such as netdev-ssh-mcp would then log in to that host with the operator's credentials. Under `lab-open`, made-up names such as `lab-ghost-99` and `lab-x@core-rtr-01` were also `allow lab-writes-free`, with no dry run in M1. Now `lab-sw-01`, `lab-sw-02` and `lab-srl-01` are listed with the lab devices already there. Any name not listed is `deny default:unknown_target`. The pattern shape stays in the file, commented out, with the hazard next to it. inventory-schema section 4, the `lab-open.yaml` header and the PLAN resolver table now describe patterns as optional and give the reads warning. Section 4 also says what the code does: any pattern match makes a name known. `TestRepoExampleInventory` checks that none of these names resolve. The threat model gains a row for this; it stays open in general, with follow-ups in M1-18 (target-name validation) and an inventory ADR.
- The audit signing key is checked every time it is loaded (M1-09, ADR 0028; from the security review of PR #112). `audit.LoadKey` read it with `os.ReadFile`, following a symbolic link and checking no owner, mode, link count, Windows DACL or macOS ACL, so another local user could make fathomgate sign with a key they hold. It now reads through the new `internal/secretfile`, the check listen token files already had: opened without following a final symbolic link or reparse point, then on the open file a regular file with exactly one link, owned by the current user, mode `0600` or `0400` with no macOS extended ACL, or on Windows a protected DACL granting only the owner and `SYSTEM`. A group-readable or group-owned key is refused, and no flag skips a check. The error names the path and the failed check, never the key; refusals match `secretfile.ErrUnsafe`. Keys `audit keygen` writes pass unchanged; a Windows key created before T0.12 with an inherited ACL is now refused (fix it with `icacls`, or generate a new one). Listen token files use the same code, with the same messages. The redaction key gets the check in M2.
- `fathomgate audit verify --key` accepts only a public key (ADR 0028). It used to accept the signing key and derive the public half, so a verification needed the secret. A file that contains `PRIVATE KEY` anywhere (a block, a corrupted block, or text before or after the public block, which `pem.Decode` would skip) now exits 2 with `--key must be the public key (<path>.pub); a verifier never needs the signing key`; `audit.LoadPublicKey` returns `audit.ErrPrivateKey`. The public key is opened without blocking and must be a regular file, so a named pipe cannot hang `audit verify`. Both key loaders accept exactly one PEM block of at most 16 KiB, with only white space around it and no PEM headers. On Windows, secret and public key files are opened with `SECURITY_IDENTIFICATION`, so a named-pipe server at the path cannot impersonate fathomgate. A refusal from `internal/secretfile` unwraps to `ErrUnsafe` and to the system error behind it, if any. Not checked, by decision: NFSv4 ACLs outside macOS, and the directories above a key file (threat model).
- On Windows, `fathomgate serve --listen` now defends against the port-squatting case that needed no race (M1-27, ADR 0029 decision 4, accepted in part: the Windows exclusive bind in M1, TLS deferred to M2). After binding `127.0.0.1:P` and `[::1]:P` it binds the same port on `0.0.0.0`, on `[::]` IPv6-only and on `[::]` dual-stack, never listening, and holds them until it stops. While they are held no other socket can bind the port on a wildcard or loopback address, with or without `SO_REUSEADDR`. So another local program can no longer bind a wildcard while fathomgate runs and collect the agents' tokens once it stops. If a wildcard on the port is already held, fathomgate exits 1 naming it, before the upstream starts, as it does when a loopback address is taken. This is mitigated by design; it was measured only with same-user sockets, and the other-user case, which is the threat (a same-user attacker can already read the token file), is to be measured. The loopback sockets also carry `SO_EXCLUSIVEADDRUSE`, which Microsoft documents as stopping any other socket binding the same address and port ("Using SO_REUSEADDR and SO_EXCLUSIVEADDRUSE"). On Windows 11 build 26200 a same-user takeover already failed without it, so that is defence in depth. If the option cannot be set the bind fails and fathomgate exits 1. Linux and macOS are unchanged: a listening socket already stops such binds there (`cmd/fathomgate/listen_unix.go` says why), and a new Linux test checks it. A squat while fathomgate is down or restarting stays open on every platform until TLS on loopback in M2.
- Under `serve --policy`, a `--server` with no profile is an empty profile, not the fallback classifier: a call carrying any argument is denied with `default:bad_arguments` (M1-20, PR #171; orchestrator decision recorded in ADR 0027). The fallback found no target, so the unknown-target default and `max_devices` did not apply to that server.
- `serve` refuses a policy, inventory, `--profiles` directory or profile file that anyone but its owner and the administrators can change (M1-20, PR #171, `internal/configfile`): on Unix a group or other write bit, or an owner other than you or root; on Windows a write entry for anyone but the owner, SYSTEM and Administrators. - A policy, inventory or profile that does not load no longer prints the surrounding lines of the file, which could include a device password (M1-20, PR #171, `internal/yamlstrict`; affects `serve`, `policy eval` and `policy test`). Errors keep the line, column and message; a message that would quote a value keeps only the position. A second YAML document in one of these files is now an error instead of being ignored, and so is an empty document before the content, which made the file load as empty.
- Reads to unknown hosts no longer pass under a policy that omits `defaults.unknown_target` (M1-37, ADR 0032; security reviews of PR #154 and PR #158). eos-mcp and netdev-ssh-mcp log in to whatever host the agent names with the operator's device credentials, so the old default let `reads-anywhere` send them to a host such as `core-x.attacker.example`. Not live in v0.1.0, which enforced no policy; `serve` applies it once the gate is wired (M1-18, M1-19). Two residuals were left open: a hostname-pattern hit made a target known, so the default did not run for `core-x.attacker.example` under an operator pattern `^core-` (closed by M1-34, ADR 0031, see Changed); and a call with no targets skips the default until the normaliser refuses zero-target calls to tools that take a target (M1-18). `policy-lint` now warns on an explicit `unknown_target: allow`. Threat model row added.
- A secret scanner runs in CI (M1-42). The new `gitleaks` job in `.github/workflows/ci.yaml` scans each pull request's commits, and on every push to `main` and weekly it scans the full history. It runs on a GitHub-hosted runner with a read-only token. It uses gitleaks 8.30.1, the upstream release binary fetched by `make secrets-scan`. The binary is checked against the sha256 pinned in the `Makefile` when downloaded and re-checked before each use; there is no third-party action. `tools/secrets/scan.py` drives it. A pull request's commits are scanned twice, with its own `.gitleaks.toml` and `.gitleaksignore` and with the base branch's, so a pull request cannot silence its own finding. Merge commits are scanned by their first-parent diff, so a secret added in a merge or a conflict resolution is found, including a multi-line one such as a second private key. They cover crypt, Cisco type 4, 8, 9, `$14$` and `$9$` hashes, type 0, 3 and 7 values, SNMP communities, FortiOS `ENC` and PAN-OS `-AQ==`, and run only on `tests/fixtures/`. Its one allow-list passes a secret in a named fixture file only when the secret starts with `FAKE`. The first line of defence for fixtures is `TestFixtureCorpus` in `internal/redact`. It now fails when a listed secret does not start with `FAKE` (after the vendor's marker), or when the redactor replaces a value that the expect file does not list. - `internal/proxy` Streamable HTTP handler (T0.27, ADR 0016), served by `fathomgate serve --listen` since T0.31 (above): `(*Proxy).HTTPHandler(HTTPOptions)` serves `/mcp` for both eras through a dispatcher on `MCP-Protocol-Version` in front of a stateful and a stateless go-sdk handler that share the one server. Checks in order: a non-loopback `Host` on a loopback bind gets 403, and so does any `Origin` or cross-site `Sec-Fetch-Site`, on every method and before authentication, with no CORS headers. Other paths get 404. A bearer token is required (401 with `WWW-Authenticate: Bearer`); tokens are named principals, kept as SHA-256 digests and compared in constant time, and a principal is attribution only. POSTs in flight are capped at 64 overall and 32 per principal (503 with `Retry-After: 1`), and stateful sessions at 16 overall and 4 per principal. Every 401, 403, 404, 413 and 503 closes the connection. Tool calls in flight are capped at 8 per session and 32 per principal and refused before the upstream. The body limit is 4 MiB. Every write to the agent has a 10-second deadline, so an agent that stops reading costs a bounded time. Deleting a session, fathomgate's own 30-minute idle expiry (no POST in progress) and `Proxy.Close` cancel the session's calls before closing it. A stateful upstream's prompt is relayed only when the one call in flight and every call that ended in the last `OrphanTTL` (5 minutes) on that upstream belong to the same agent session (T0.38, T0.40). `JSONResponse` stays off, and a test pins that no progress follows a result. ### Security

- `fathomgate serve --listen` binds both loopback families on its port (T0.52; H1 in the post-merge security review of PR #109; [ADR 0023](docs/adr/0023-listener-binds-both-loopback-families.md), accepted). `--listen localhost:P` or `127.0.0.1:P` bound only `127.0.0.1:P`, so another local user could bind `[::1]:P` and receive the bearer token of an agent configured with `http://localhost:P/mcp` that tried `::1` first; `[::1]:P` had the reverse gap. fathomgate now binds the address asked for and then the other family's loopback on the same port, serves both, and logs one `listening url=...` line for each. If the other address is taken, it exits 1 before the upstream starts, naming the address; with port `0` it retries on a new port; a host without that family logs a warning and serves on one. `--listen` now takes only `localhost`, `127.0.0.1` or `[::1]`: another `127.0.0.0/8` address, bound alone, left `127.0.0.1` and `[::1]` on its port to other users, and exits 2. A new connection must deliver its first request's headers within 3 seconds (L1); the 128-connection cap is shared by both addresses. The install guide says to paste the exact URL from a `listening` line and to restart fathomgate at once when it stops (port squatting while it is down is open until M1).
- Token files, the audit signing key and the audit log with a macOS extended ACL are refused (T0.52, L2). The owner-only checks read the mode bits, which do not show an ACL entry such as `everyone allow read` set with `chmod +a` or inherited from the folder. `internal/fileacl` reads the ACL with `fgetattrlist(2)` on the open file, without cgo; CI runs the tests with real ACLs on `macos-latest`.
- A launcher's server no longer outlives its upstream (T0.46, [ADR 0021](docs/adr/0021-kill-the-upstream-process-tree.md); S2 in the security review of PR #77). A stdio upstream now starts in a process group of its own on Linux and macOS (`Setpgid`) and in a Job Object of its own on Windows (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, no breakaway), so the server behind `uvx`, `npx`, `uv run` or a shell script is part of the upstream's tree. On Windows the upstream is created suspended, assigned to its job and then resumed, so nothing it starts can run outside the job; if the job cannot be created, assigned or resumed, the upstream is killed and startup fails. The ADR 0018 restart, every failed startup attempt and the startup budget running out now kill the whole tree (`SIGKILL` to the group, or `TerminateJobObject`), so the first copy of the server no longer keeps running, with the `--upstream-env-pass` credentials in its environment, beside the second. Startup now meets its 30-second budget on those paths instead of overrunning it by up to 2 seconds (the `exec.Cmd` `WaitDelay`, which stays as a backstop). On shutdown the group gets `SIGTERM` and `SIGKILL` 250 ms after go-sdk sends each to the upstream (5 and 10 seconds after its stdin closes), and on Windows the job is terminated when go-sdk kills the upstream. Once the upstream has been reaped, on shutdown and when it exits mid-session, what is left of its tree is swept once: `SIGTERM`, up to 2 seconds, then `SIGKILL` (only `SIGKILL`, with no wait, when the group has already been sent it); the job is terminated on Windows. On Windows the tree also dies if fathomgate itself crashes. The first `EPERM` on a group signal (a setuid launcher) is logged at Warn. This is containment, not a sandbox. Residuals: a descendant that calls `setsid()` or `setpgid()` leaves the group on Unix; on Windows any descendant can start a process outside the job by naming a same-user process outside the job, fathomgate included, as its parent, or through a service; a setuid launcher's member may not be signalled; a container behind `docker run -i` is never in the tree; fathomgate as PID 1 in a container needs `docker run --init`; a fathomgate crash on Unix still orphans the tree (run it under systemd); an upstream that reads the controlling terminal is stopped (`SIGTTIN`) in an interactive shell. `internal/proxy` imports `golang.org/x/sys/windows` on Windows (ADR 0011 amendment row); `CGO_ENABLED=0` still holds. New CI job `go test (macos)` runs `go vet ./...`, `go test ./...` and `go test -race ./internal/proxy/` on `macos-latest`; it is not a required check yet.
- The install guide now requires netdev-ssh-mcp v1.7.1 (T0.51). v1.6.6 and earlier leave some secrets in clear or reversible ([GHSA-8g43-jrf3-q9vq](https://github.com/krisiasty/netdev-ssh-mcp/security/advisories/GHSA-8g43-jrf3-q9vq), fixed in v1.7.0, reported by Fathomgate in T0.29), and v1.7.0 and earlier let a tool call make the device run further commands ([GHSA-h47r-329w-6p9h](https://github.com/krisiasty/netdev-ssh-mcp/security/advisories/GHSA-h47r-329w-6p9h), fixed in v1.7.1). Upgrade if you followed the earlier guide. The guide keeps the upstream's default per-run obfuscation key and presents a key file as optional, kept where the agent's tools cannot read it.
- A tool call that arrives over the HTTP listener can no longer be read as the local stdio agent's if go-sdk stops copying the HTTP request into the call (T0.31; L1 in the security review of T0.48). The listener marks the context of every authenticated request, `transportOf` reads the mark as `http`, and a call that reads as `http` with no principal is refused with `fathomgate refused <server>.<tool>: the request arrived over the HTTP listener without an authenticated principal` before anything is keyed or forwarded. `fathomgate serve` also never runs the stdio agent and the listener in one process.
- An MRTR `requestState` is bound to the agent side it was issued to (T0.30, ADR 0016). fathomgate now issues sealed envelopes (then `ng3.`, `fg4.` since the rename) whose AES-GCM additional authenticated data is the transport (`stdio` or `http`) and the principal (the listen token's name; empty on stdio), so a retry from another principal or over another transport is refused with `-32602` `invalid_request_state` and the same detail as a forged envelope, naming neither side, and nothing reaches the upstream. `ng2.` envelopes from before the upgrade could never open (the key is per process) and now get `requestState was issued by an earlier fathomgate process; call the tool again without it`. A refused `requestState` is logged at Warn with the presenting transport and principal, rate-limited. The call `Proxy.dispatch` receives carries the transport beside the principal; a principal remains attribution only. Each progress mapping belongs to its one agent request through a token that is fresh for that request and never shared by two. profile-schema 8.4 states the cross-session attribution rule.
- A same-principal MRTR retry that keeps a valid `requestState` but changes the tool or the arguments is now logged at Warn, like a state that does not verify (T0.48, L2 in the post-merge security review of PR #85). It was refused with `-32602` and nothing reached the upstream, but no line recorded it. The line names the presenting transport and principal, the server and the tool the retry was presented on, and fathomgate's own reason (`requestState was issued for another tool` or `arguments differ from the call that asked for input`); it quotes no argument and nothing from the envelope. It shares the refusal rate limiter, keyed by server, transport, principal and reason. The progress relay no longer carries the session key, transport and principal fields T0.30 added: nothing read them, and the per-request guarantee is the upstream token, which is now drawn only in `watchProgress` (L1). ADR 0016 amendment row, profile-schema 8.2 and 8.4 and the threat-model rows "Progress token scope" and "Cross-principal `requestState` replay" say so; the latter now states the 30-minute same-token replay residual in full, and the stdio-side one: a listener call with no go-sdk `Extra` would bind as the local agent's `{stdio, ""}`, safe only while `fathomgate serve` keeps the two sides exclusive (T0.31 must fix or re-state it).
- One principal can no longer hold every other principal's stateful upstream prompts in refusal without a trace (T0.44, S2 and S4 in the post-merge security review of T0.40). Every stateless per-request call, and every session past 1024 per upstream, used to share one orphan entry that was foreign to every session and never pruned, logged or attributed. Now each call fathomgate cannot name to a session gets an orphan key of its own (`r` and a per-proxy counter; a stateless agent's session is never keyed by an id), so its ended call is an ordinary record: pruned at `OrphanTTL` and logged at Info with its principal when reaped. Each refusal of an upstream prompt is logged at Warn with the principals behind it (`ended_calls_of`, `in_flight_of`, or the attributed call's `principal`), at most once per 10 seconds per server, attribution, class and principal set, with a `suppressed` count (and `suppressed_lost` when the limiter's table is swept). The 1024-entry table cap is now a quota of 256 records per principal per upstream. Past it, that principal's further ended calls fold into one overflow record of its own, which fails closed, refuses that principal's own sessions' prompts too, is logged at Warn when made (expected for a 2026-era agent above about 0.85 calls a second to one upstream) and at Info when reaped, and cannot push another principal's records out. The residual is accepted by the maintainer (2026-09-24): a principal that keeps ending calls, or holds one open, on a stateful upstream keeps other sessions' prompts on it refused while it does; the only recourse is removing its token. M3 needs a per-upstream prompt policy or principal binding (new Open threat-model row).
- A stateful upstream's prompt refused by the orphan rule can no longer put fathomgate's text in place of the upstream's own error (T0.42, S3 in the post-merge security review of T0.40). When the one call in flight could not have been prompted anyway (ADR 0014, or no form elicitation), fathomgate recorded the refusal as that call's own, and an upstream error for the call was then replaced by it, although the prompt was exactly one fathomgate could not attribute to that call; a hostile upstream could trigger this at will and speak in fathomgate's voice about why a call failed. The refusal is now a note on that call only: appended to a result the upstream completes, never in place of an upstream error or result, which is what SECURITY.md promised. Over the HTTP listener a 2026-era agent calling a 2025-era upstream that fails the call now gets the upstream's error, which may quote the ADR 0014 refusal (a go-sdk upstream does), instead of fathomgate's tool error. Test `TestOrphanRefusalNeverReplacesUpstreamError`.
- The local stdio agent is keyed as its own session whether or not an HTTP handler has been built (T0.43, S1). The key came from whether the proxy had a listener: once `HTTPHandler` had run, the stdio session (which has no session id) was keyed into the shared orphan entry, and after its first call no stateful upstream prompt reached anyone on that upstream for `OrphanTTL`, renewed by its own traffic. Latent until `--listen` (T0.31). `Proxy.Run` now records the session it serves and gives it a key of its own (`l1`, `l2` for a second `Run` on one proxy, which only tests do), so two agents on one proxy never share a key either. A request on the local session that go-sdk dispatches while `Run` is still connecting waits for that record without any lock held across the connect, and gets the shared entry only if its context ends first; a call over the HTTP listener never waits (it is keyed by its session id or gets the shared entry). Tests `TestListenerCallNeverWaitsForRun`. `Run` wraps a connect failure as `proxy: connect agent session: ...`. Tests `TestLocalAgentOwnOrphanWithListener`, `TestLocalKeyDuringConnect`, `TestAgentSessionKey`; `TestProgressStuckAgent` and `TestEndBeforeFinish` now expect the orphan refusal between their two in-process agents before the orphan expires.
- The documented residual of the orphan rule is corrected (T0.44, doc part; S2 and S4): the shared orphan entry (every stateless per-request session, and every session past 1024) is not pruned, not logged and not attributed to a principal yet, so a refusal it causes cannot be explained from the log, and "up to `OrphanTTL`" bounds one ended call, not the steady state: one principal can keep every other principal's stateful prompts refused on an upstream with one stateless request per `OrphanTTL`. This is recorded as **open**, not accepted: its own threat-model row ("Cross-principal refusal of stateful prompts via the shared orphan entry", owner mcp-protocol-engineer), T0.44, which must land before `--listen` (T0.31). The code fix needs a maintainer's choice. The residuals also state that which refusal an agent sees reveals whether another session ended a call on that upstream within `OrphanTTL`.

- A stateful upstream's prompt that arrives after its call finished **normally** no longer reaches another agent session's human (T0.40, J1 in the re-review of PR #72). fathomgate remembered only cancelled calls, so a call the upstream had answered left nothing behind; an upstream that kept working on it in the background, or whose prompt go-sdk dispatched after its result, could then have that prompt attributed to whichever other session had a call in flight, and that human's answer went back as the answer to the first call (confused deputy, MCP03). Every call that ends is now remembered as an orphan of its agent session, cancelled or not, and a prompt is relayed only when the one call in flight and every live orphan on that upstream belong to one session. That window is its own option, `HTTPOptions.OrphanTTL`, **5 minutes** by default instead of the 30-minute idle `SessionTimeout` it used to borrow (J3), and reaping an orphan is logged at Info with the server and the principal it was blocking for. Where the one call in flight could not have been shown any prompt anyway (a stateless agent, ADR 0014), the refusal still says so. Accepted residual: with more than one agent session on one upstream, a stateful upstream's prompt is refused for up to 5 minutes after any other session's call ends. Tests `TestHTTPPromptAfterFinishedCall`, `TestOrphanTTLSeparateFromIdle`, `TestOrphanReapedLogsPrincipal`, `TestAgentSessionKey`; rules in `docs/specs/profile-schema.md` sections 8.4 and 8.5; threat-model row "Stateful upstream prompt for a call that ended normally".
- `fathomgate serve` no longer echoes an argument that could be a password (T0.23, ADR 0017, security review of #64): a stray positional (`--upstream-env DEVICE_PASSWORD FAKE-x` put the password there), an unknown flag (`-FAKEx`), bad flag syntax, a malformed `--upstream-env` argument and a bad key are all reported by position only (`unexpected argument N; ...`, `unknown flag at argument N`, `--upstream-env argument N: key must match ...`); the flag package's own messages are discarded, and a reserved flag after `--` is named without its `=value`. `--upstream-env FATHOMGATE_*=...` is now refused with exit 2 (ASCII case-insensitive on Windows), as `--upstream-env-pass FATHOMGATE_*` is, so neither flag can hand an upstream fathomgate's own settings. Canary tests cover every error path. Accepted residual: a value typed where a name belongs is named by the `--upstream-env-pass` "not set" error.
- A slow agent can no longer stall an upstream through the progress relay (T0.28, security review S2 on PR #53). go-sdk dispatches an upstream's notifications and requests one at a time, and the relay wrote each progress notification to the agent on that goroutine while holding the call's lock. An agent that stopped reading therefore held up every later message from that upstream, another call's `elicitation/create` included. When the call's result then arrived, its end waited on the stalled write and left a stale in-flight entry, which broke the attribution of a stateful upstream's prompts. The relay now only queues. One sender goroutine per call writes to the agent from a queue of at most 10 (when the queue is full the newest entry is replaced, so progress still increases). At the end of a call fathomgate waits at most 1 second for the queue to be written, then drops the rest and releases the call. Nothing follows the result. A notification the rate limit held back is now sent as soon as a rate slot frees up, not only before the result (S4). Rules in `docs/specs/profile-schema.md` section 8.4, "Delivery"; threat-model row "Upstream notification queue blocked by a slow agent" is now mitigated.
- The golangci-lint binary is verified before it runs (T0.20). CI used `golangci/golangci-lint-action` v9.3.0, which downloads the release archive and extracts it without checking a hash or signature. `make lint` now downloads golangci-lint v2.9.0 (version unchanged) itself, checks the archive against a sha256 committed in the `Makefile` for linux and darwin on amd64 and arm64 (taken from the release's `checksums.txt`; the linux-amd64 archive also passes `gh attestation verify`), and only then unpacks it. The CI `golangci-lint` job runs `make lint` in place of the action, with `persist-credentials: false` and `make toolchain-check`. The local fallback to `go vet` when golangci-lint was not installed is gone, and `make lint` type-checks for `linux/amd64` under the `go.mod` toolchain, as CI does. The reasons are in `CONTRIBUTING.md`.
- The container base images are pinned by digest, not only by tag (T0.15): the `Dockerfile` builder is `golang:1.26-alpine@sha256:8ac98ca534ac3f51e1f420a1dd2c15e74c75cfa0f23f3ad27eb5d7236c349a0c` (go1.26.8), and the distroless runtime in `Dockerfile` and `Dockerfile.goreleaser` (the base of every release image) is `gcr.io/distroless/static-debian12:nonroot@sha256:afa5c872c891853ca7fcf1f12c3edb23f7eeef36189728842dd51042ff57f7ab`. Each digest is the multi-arch OCI image index, resolved on 2026-09-23 with `docker buildx imagetools inspect` and confirmed against the registry's `Docker-Content-Digest` header. A retagged upstream image can no longer change what we build or ship without a reviewed pull request; the existing Dependabot `docker` entry proposes digest updates for both files.
- The audit checkpoint private key and the audit log are owner-only on every OS (T0.12). `audit.SaveKey` (and so `fathomgate audit keygen`) creates the key exclusively and never overwrites an existing file or symlink. On Unix it uses `O_EXCL` and `Chmod(0600)` on the descriptor, so `keygen --out` onto an existing `0644` file is refused instead of leaving the key world-readable. On Windows, where `0600` did nothing and the key inherited its folder's ACL (for example `BUILTIN\Users` read under `C:\ProgramData`), it is created by `CreateFile` with a protected DACL granting only the current user and `SYSTEM`, so a local non-admin user can no longer read the key and re-sign checkpoints over a rewritten log. `audit.NewWriter` creates a new log the same way and never truncates. An existing log is opened without following links and refused unless it is a regular file with one link (no symlink, junction, reparse point or hard link) owned by the current user, so a writer running as root or SYSTEM can no longer be pointed at another file and change its permissions. The chain is verified through the held handle, and only then is the log reset to owner-only (mode `0600` or the protected DACL), which strips any read access granted to a log shipper. On Windows every new key, public key and log is created with `FILE_FLAG_OPEN_REPARSE_POINT`, so a dangling symlink planted at the path cannot redirect where the file is created. `keygen` also refuses an existing `<out>.pub`, writes the public key first through the new `audit.WriteKeyPair`, and deletes it again if the private key fails; partial files are deleted through their handle. The interim `icacls` guidance in `SECURITY.md` is replaced by what the code guarantees.
